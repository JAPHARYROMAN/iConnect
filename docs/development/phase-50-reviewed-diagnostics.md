# Reviewed diagnostic reports

Both native applications now offer a reviewed JSON diagnostic snapshot with deliberate local export. The report is constructed from an explicit field list; no state, settings, receipt, exception or log object is serialized wholesale. This closes part of the diagnostic-export requirement while leaving complete local operation/security history and retention controls open.

## Included and excluded fields

Schema 1 contains public app/OS versions, a UTC capture time, a best-effort-snapshot flag, coordinator/direct connection states, whether coordinator/STUN settings are configured, owner-policy health, pairing/approval counts or presence flags, availability options, aggregate queue counts/phases and fixed recovery-area counts. Windows includes only the number of retained activity entries, with `entriesIncluded: false`. An unavailable active-worker count is `null`, rather than an inferred zero. Snapshots are observational and can contain values read at different instants; they never authorize work or establish a successful network/security test.

The JSON omits device names and identifiers, peer names/identifiers, public/private keys, pairing invitations/codes/tokens, session/transfer/grant IDs, coordinator/STUN addresses, filesystem paths, provider URIs, filenames, content/hashes, receipt descriptions, activity text and raw errors. Recovery area keys and phase names come from compiled mappings/enums, rather than user or remote text. Reports are bounded to 32 KiB. Counts and timestamps can reveal usage, which both review screens explain.

The report is a limited support snapshot, not a complete audit trail. It does not establish that every operation was logged, diagnose a specific NAT failure, prove direct internet traversal or attest that received content is safe. It includes no raw connection-error detail; Windows records only whether an error was reported. Support may still need a separately reviewed description of the visible failure.

## Review and export

Both screens display the exact JSON before choosing a destination. Review permission is single-use, current-process only and expires after two monotonic minutes. Cancellation, changed/forged reviews, owner-context changes and controller recreation reject earlier permission. Owner recovery/reset and controller closure invalidate pending reviews. Reports remain available when owner policy is blocked, without repairing that policy or enabling sharing.

Windows uses a folder picker and a new `iConnect-diagnostics-<random-token>.json` file. It holds a native destination handle, excludes the current private profile and sensitive/system locations, creates without replacement, flushes and verifies exact read-back bytes. An existing name is preserved. A failed write may leave a new incomplete report; retry requires another review. Native window/keyboard/screen-reader verification remains stopped following the user's physical Escape.

Android uses the system create-document contract with `application/json`. Opening that picker may background iConnect and end unrelated storage availability as usual. An already reviewed snapshot can still be saved through its pending token; this does not resume a connection or restore transfer authority. The writer requires a document URI, opens it read/write without truncation, checks for an empty regular single-link descriptor, writes/flushes/syncs the reviewed bytes and reads back at most 32 KiB to verify equality. Nonempty documents are kept. Unsupported descriptors and provider errors refuse completion; a provider copy may remain and is never deleted automatically. A canceled or lost activity/controller review does not silently regenerate or export a report.

Windows export creates a new file in the chosen ordinary local folder. Android writes to the document provider selected by the user; that provider may store or sync the document remotely, which the review screen explains. iConnect does not automatically send a message/support bundle, invoke a share sheet or grant remote access. The report contains no stable installation identifier; its randomized filename is only a local collision-resistant name.

## Verification and remaining gates

The Windows Release solution and WinUI build pass with zero warnings/errors. Five focused controller cases pass: poison inputs in actual settings, trust, filenames, private snapshots, hashes, activity and raw diagnostics are excluded; saved bytes equal the reviewed JSON; canceled/forged/replayed reviews do not write; collisions preserve owner bytes; private-profile destinations are denied; owner reset/reopen end permission; and blocked-policy reporting keeps the private recovery reason out of the report. The full Windows regression passes **466 selected cases in 2 minutes 41 seconds**, with the same three separate capacity exclusions as phase 49. Evidence: `.tools/phase50-windows-build.log`, `.tools/phase50-windows-diagnostics.log` and `.tools/phase50-windows-regression.log`.

The first Android debug, instrumentation and unsigned release builds pass, together with 39 JVM tests and lint with zero errors and 67 existing warnings. Its first focused run passed four of seven cases. The remaining cases stopped at `DocumentsContract.isDocumentUri`: the test-only provider lacked the `android.content.action.DOCUMENTS_PROVIDER` intent filter required by the [Android provider contract](https://developer.android.com/guide/topics/providers/create-document-provider). The fixture declaration is corrected; production validation remains intact. Granted URI access makes the supplying provider visible under Android's [package-visibility rules](https://developer.android.com/training/package-visibility/automatic), without requesting broad package visibility. Evidence: `.tools/phase50-android-build.log` and `.tools/phase50-android-diagnostics.log`.

The second focused run passed six of seven cases: the remaining replay case reused a generated filename that the provider correctly refused to create again. Its fixture now uses distinct names. An expanded eight-case run reached an actual system-picker save, then failed in test cleanup after the activity closed and its temporary URI grant ended. Cleanup is now inside the still-live activity. These were fixture/declaration/lifecycle corrections; the destination descriptor and review checks remain intact. Evidence: `.tools/phase50-android-verified-diagnostics.log` and `.tools/phase50-android-complete-diagnostics.log`.

The final Android debug, instrumentation and unsigned release builds pass, together with 39 JVM tests and lint with zero errors and 67 existing warnings. One overlapping build was stopped by an earlier build's daemon cleanup; the final build was rerun sequentially and completed before device verification. Evidence: `.tools/phase50-android-verified-complete-build.log`.

All **eight focused device cases pass in 6.886 seconds**. They cover poisoned full state, exact provider bytes, cancellation, forged/superseded/replayed reviews, monotonic expiry, owner/context and controller changes, refusal of non-document URIs, and preservation of existing provider bytes. The native review/cancel/save component passes with generated provider documents. A separate actual Android system-picker journey cancels once, returns to the app, prepares a fresh report, chooses Save and verifies the exact JSON through the returned document URI. It exercises the real activity stop/start boundary, keeps sharing and authentication disabled, and removes its generated report before the temporary grant ends. Physical devices and other chooser/provider implementations remain separate gates. Evidence: `.tools/phase50-android-final-diagnostics.log`.

The broad Android regression passes all **321 selected device cases in 421.631 seconds**, including all eight diagnostic cases and the existing storage, transfer, recovery and native screen suites. It uses the same four coordinator-dependent interoperability-class exclusions and four separately recorded full-capacity exclusions as phase 48. Evidence: `.tools/phase50-android-regression.log`.

The final application APK SHA-256 is `41a5507a9ee92bb05fe8b106b2224921b9094759b36bc93c1bb63bc68802c1ba`; the test APK SHA-256 is `830fe99939b34a232a29bb66f1b613fdd268c1541d93a700576a6d86dd25d937`. Installed hashes match the built files before and after final device verification. The owned headless emulator was stopped afterward. These remain development APKs; the release APK is unsigned. An earlier failed system-picker test left a generated diagnostic report on the disposable emulator after its temporary grant ended; the corrected focused and broad journeys remove their own new reports while the activity remains open.

Supported provider/volume matrices, blocked/unavailable storage, provider open/read/write deadlines, cancellation and actual process/power-loss durability, maximum-load responsiveness, native accessibility, independent privacy/security review, signing/packaging and release documentation remain open. Controller initialization must succeed before in-app diagnostics can be used; this feature is not a repair tool for an application that cannot start. Local audit/history coverage and configurable retention remain in the [completion audit](completion.md). The [physical-network procedure](physical-network-validation.md) remains for the user to execute after implementation.
