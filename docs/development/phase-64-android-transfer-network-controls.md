# Android transfer network controls

Android now has its own saved payload bandwidth limit and optional pause on metered or unknown networks. The owner reviews changes through a native dialog. Defaults are unlimited bandwidth and metered pausing off. These preferences belong to this phone; they cannot determine the computer's network plan or charges.

## Peer payload policy

`PhoneFileTrafficPolicy` shares one sending budget and one receiving budget across the controller's peer sessions, files, batches and remote previews. Limits can be unlimited or 64 KiB/s through 64 MiB/s, with matching Windows presets. Saved custom values in the valid range remain visible. Monotonic elapsed time drives pacing and observation freshness.

`RemoteFiles` checks content preparation, file ranges, upload writes, batch admission/manifests and batch creation/writes before calling the document service. Existing foreground, pairing, grant and selected-background-ticket checks still apply. Metadata with an attached payload cannot bypass this gate. Bounds are checked before waiting. Outgoing requests are immutable, acquire a bounded RPC credit before pacing and start their response timeout afterward. Closing the RPC cancels requests waiting on bandwidth as well as requests awaiting a response. Pending request/waiter collections are safe across cancellation and response completion.

Read requests are paced before asking for bytes; incoming writes are paced before processing and acknowledgement. Costs and settings health are checked again during waits and before transmission. Changing a limit is observed by waiting ranges. Status, release, cancellation and finalization remain usable within their existing storage/lifecycle authority when content is blocked. The synthetic diagnostic transfer also checks and paces content. Its native event actor now accepts suspending handlers without blocking the channel callback.

These are **application peer-payload controls, not an OS traffic or billing cap**. They exclude protocol overhead, signaling, metadata, retries, already buffered/in-flight data and unsolicited traffic from a hostile peer. Incoming write bytes arrive before their processing/acknowledgement can be delayed. Document providers may independently fetch or synchronize cloud data; this policy does not control those providers' networking. Local copies and local management remain independent. Configuring both endpoints can lower throughput further.

## Cost and lifetime

The monitor checks Android's process-bound/default network and its capabilities, not an assumed cost based on Wi-Fi/cellular labels. Missing internet/general-use capability, a missing network, read failure or a network that changes during observation yields unknown. Absence of the normal unmetered or non-roaming capability, or an enabled Android background-data restriction, is treated conservatively as metered. This does not prove the actual WebRTC route. See Android's [network capabilities](https://developer.android.com/reference/android/net/NetworkCapabilities#NET_CAPABILITY_NOT_METERED) and [metered-network/data-restriction APIs](https://developer.android.com/reference/android/net/ConnectivityManager#isActiveNetworkMetered()).

Cost polling runs every two seconds only while the UI is visible or an already-approved foreground-service transfer remains selected. No new network request or background authority is created. Stopping those reasons publishes unknown; old query results cannot reactivate an observation. The query does not hold the lifetime lock, so a slow native call cannot block stopping the observer. Readings older than five seconds become unknown. Production uses Android elapsed realtime, including device sleep.

When enabled, metered/unknown pausing refuses subsequent content requests. Existing receiving/sending error paths retain stopped work for explicit resume; a later unrestricted observation does not restart stopped jobs. Batches retain their foreground-only rule, and a single-file background permit cannot become general browsing authority. The observer stops when a session ends and clears its selected background work.

Existing source-approval and operation expiries are unchanged. A very slow/large transfer can outlast its approval. The limiter does not silently extend authorization; lifetime-aware estimates and reviewed fresh-source recovery remain separate work.

## Persistence and recovery

`AndroidTransferNetworkSettings` stores bounded schema-1 JSON under `transfer-network`, containing only the numeric limit and pause flag. It uses the existing synced/read-back atomic writer, an exclusive native lease, directory identity and exact record stamps. Strict keys/types, schema/range validation and symlink/hard-link checks protect the record. A running instance refuses a changed directory or record identity when saving. Unexpected records are kept rather than overwritten; failure to open storage produces a blocked content policy.

Fresh stores persist defaults. If a previously opened store loses its settings file, content stays blocked until owner review; a reappearing record prevents missing-state reset. Corrupt/uncommitted/invalid settings also block content. An owner can preserve damaged metadata, reset to explicitly reviewed defaults and separately remove preserved metadata backups. These actions do not delete provider files, transfer receipts or sharing approvals. Coordinated deletion/rollback of the entire profile and hostile same-UID interference are not established as solved.

If settings storage cannot open, the controller still provides the local explorer with a blocked remote-content policy. Preference writes use the existing IO persistence lifetime; controller shutdown waits for them before closing the settings lease. Cost observations do not serialize network names, IDs, addresses, peer IDs or file paths into settings or history.
