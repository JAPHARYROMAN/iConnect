# Android sender checkpoint cadence

The ordinary Android sender previously rewrote its private journal after every validated 32 KiB acknowledgement. The receiver already syncs each accepted range and saves its checkpoint before acknowledging it. The sender's local offset is a restart hint: every resume queries the original receipt, validates its descriptor and uses that fresh offset before sending more bytes.

The candidate retains live validated acknowledgements in the existing memory-only payload flow. It saves the sender offset after 1 MiB of newly acknowledged progress or one second since its last save, whichever is reached first at an acknowledgement. A backward monotonic-clock observation also saves immediately. A stalled request does not trigger a timer or extra work. The final payload acknowledgement, phase changes, pause and ordinary failure retain their existing durable save paths.

The original receiver ID/epoch is still committed before admission. Receiver synchronization, checkpoint chains, duplicate-range validation, source hashing, current pairing/grant/foreground checks, cancellation and final publication verification are unchanged. A lost reply cannot advance the sender's validated progress. A crash can leave the sender hint behind the receiver; explicit resume rechecks that same receipt rather than creating another copy. Journal-write failure continues to block sending and preserve copies for review.

## Why measure this path

The [first allocation comparison](upload-cost-profile.md) demonstrates no upload speedup. A subsequent [CPU sampling record](evidence/android-upload-cpu-2026-11-09.json) uses the unchanged `6eab422c…` debug app with `846d4891…` instrumentation. Android's [Simpleperf](https://android.googlesource.com/platform/system/extras/+/master/simpleperf/doc/README.md) supports sampling Java and native stacks; the [debug application workflow](https://android.googlesource.com/platform/system/extras/+/master/simpleperf/doc/android_application_profiling.md) requires no application change.

The recorder collects 5,495 task-clock samples at 99 Hz over 150.004 seconds, with zero reported lost samples and a 64 MiB recording cap. Sender `PhoneUploads.save` appears under 9.81% of sampled CPU time; receiver saves appear under 6.02%; all `PrivateJsonFile.write` calls appear under 15.03%. These are overlapping inclusive stack percentages, not additive costs or wall-time savings. They justify examining sender saves; they do not prove the candidate is faster. Separate provider-process CPU is outside this recording. Kernel symbol addresses remain restricted. The 174.654-second probe outlasts the recording, so its final tail is not sampled. Both source/output hashes and collision preservation pass.

The first host launcher fails before starting the diagnostic. Its waiting sampler is reused, and the diagnostic completes successfully. The collection wrapper then marks failure while checking the recorder's exit status without recording that value. The retained sample file is subsequently collected and parsed successfully on-device; the exact recorder exit code remains unknown. Both original failed wrapper states are preserved in the evidence. This recovery establishes usable diagnostic samples, not a successful wrapper execution.

## Validation scope

Three new device cases cover live progress versus the saved 1 MiB checkpoint followed by pause and same-receipt completion; deadline/clock rollback; and reopening a persisted sender hint that trails five receiver ranges. The last case captures the journal before graceful pause can save newer progress and relocates its own private snapshot without changing the recorded inode. It restores that snapshot after checking fresh-receipt resume. This is an on-disk recovery fixture, not an actual process kill.

The debug/test/unsigned Release build passes in 9m 37s, with all 89 JVM tests passing and lint reporting zero errors and 71 warnings. All 87 selected device cases pass in 139.324 seconds without failures or skips, including the three new cases and the existing receiving, storage, cancellation and sender coverage. Two exact assertions on the preserved previous app establish its old per-range saving behavior; they do not demonstrate an old recovery defect.

Both encrypted native Windows–Android initiating roles pass with two 2,097,169-byte files per role, matching hashes, original-receipt resume, preserved source/collision files, fresh published-copy checks and withdrawal refusal. The Windows fixture remains `72e01283…` with 208 files, and the pinned native library remains `84a0a63d…`. The candidate app is `b8cc8e37…`; before/fixed checks use identical instrumentation `6667c887…`.

The matched 67,108,881-byte pair uses the same instrumentation, range count and owned API 35 emulator, with fresh generated bytes per run. Both source/output hashes and collision preservation pass. The [validation record](evidence/android-sender-checkpoints-2026-11-09.json) retains exact artifacts, captured sources and raw build/device/native/diagnostic evidence.
