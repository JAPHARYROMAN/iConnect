# Windows destination-side partial-file recovery

Windows receives temporary files alongside the owner-selected destination. The Transfers screen now provides a separate folder-based inspection and removal workflow for files left without current receiving references after history is lost or deliberately archived. It never adopts a filename as receiving instructions, searches child folders automatically or derives remote access from local cleanup.

## Scope and current-receipt protection

The owner chooses one ordinary local folder. Connections, automatic availability and transfer work pause before inspection. Each operation requires the current local identity, an idle receiver and healthy ownership metadata for ordinary incoming uploads, scoped batch uploads, file downloads and folder downloads. Their locks remain held during each bounded action. Current temporary tokens and recorded native file identities are protected across the profile, independently of peer grants and revocation. Folder-download child references also protect their names when separate file progress is missing.

The metadata checks reject uncommitted sidecars, changed or substituted directories, unexpected journal inventories, changed receipts and altered scoped-journal native versions. Review and continuation bind a fingerprint of the current protection inventory. Native folder identity and canonical location bind the selected destination. Changes that invalidate those bindings require another selection or review; a non-cancellation failure ends prior removal permission.

Only exact `.iconnect-transfer-<token>.part` names are candidates. A matching filename does not establish origin: a candidate can be owner data, a manually renamed file or a part belonging to another app profile. The native screen explains that limit, provides paged local inspection and requires a separate permanent-removal review with file/byte counts and typed `REMOVE` confirmation. Existing profile receipts protect recorded published-file identities even if the files have been renamed to unrelated temporary-looking names. Copies whose identity has been lost remain unidentified and require the owner's decision.

## Bounded, identity-bound removal

Inspection scans at most 32,768 immediate entries and admits at most 8,192 supported candidates. It rejects matching directories, redirected or multiply linked files and files above the existing transfer-size limit. Unsupported folders are preserved. Candidate pages contain at most 50 names and byte sizes.

A single-use review captures exact native file versions and expires after two monotonic minutes. Confirmation requires the same owner, selected native folder, protection inventory and full candidate list. Each confirmation or continuation deletes at most 64 reviewed files. A delete-capable, no-follow native handle pins each file against writers and replacement; identity/version and current protection checks precede deletion. The destination directory stays open throughout the call. New files are never added to an existing deletion list, and changed or locked files are kept for another review.

Withdrawing the recovery screen can interrupt removal between files while retaining its exact current-process cursor. The native continuation loop yields between calls. Restart requires fresh folder selection and review. Completion clears the selection, so inspecting newly appearing files requires an explicit new scan. Selecting another folder, owner reset and controller disposal end earlier permission. Recovery does not grant sharing access or contact peers.

## Verification and remaining gates

The Windows solution and WinUI application compile in Release with zero warnings/errors. The first focused run passed 9 of 15 cases; the other cases exposed fixture mistakes: an upload range shorter than the protocol permits and a source host without the required download-ticket store. Correcting those fixtures produced 15 passing cases. The expanded run passes all 20 focused storage/controller cases. Evidence: `.tools/phase49-windows-parts.log`, `.tools/phase49-windows-parts-corrected.log`, `.tools/phase49-windows-verified-parts.log` and `.tools/phase49-windows-build.log`.

The broad Windows regression passes all **459 selected cases in 2 minutes 42 seconds**, using the same three separate full-capacity exclusions as phase 46. Evidence: `.tools/phase49-windows-regression.log`.

The final focused run passes all **22 cases in one second**. Its two additional lifecycle cases use actual interrupted downloads: a folder receipt protects its real part after the separate file record is lost, and a cold-normalized interrupted download retains its part while uncommitted folder metadata blocks removal. The final Release build has zero warnings/errors. Storage, controller and WinUI production DLL hashes match before and after rebuilding the extra tests, so these checks and the broad regression cover the same production binaries. Evidence: `.tools/phase49-windows-final-parts.log`, `.tools/phase49-windows-final-build.log` and `.tools/phase49-production-hashes-before-final-tests.txt` / `.tools/phase49-production-hashes-after-final-tests.txt`.

The focused cases also cover current ordinary/scoped receipts, exact reviews and replay, current published-file identity after rename, bounded removal and pagination, new or changed files, current-process cancellation, fresh selection after reopening, peer revocation, owner-generation change, active download refusal, changed/uncommitted ordinary and scoped metadata, native destination replacement, hard links, matching directories, locked files and the actual offline controller journey without pairing or grants. Tests use generated local data, actual Windows native file identities and direct storage/controller calls; they do not establish an encrypted cross-platform workflow. Publication fixtures use an accepting attachment-check adapter where specified, so those checks make no new Windows attachment-policy compatibility claim.

Windows visual automation remains stopped following the user's physical Escape. Compilation and model checks do not establish visual, keyboard or screen-reader correctness. Maximum retained-history review/continuation latency and UI responsiveness, supported volume/storage matrices, actual process/power-loss behavior, hostile same-user interference, independent security review, packaging and release gates remain open. The bounded cleanup size does not establish maximum-capacity responsiveness of the ownership-inventory checks.

Android code was unchanged in this phase; its last evidence remains [phase 48](phase-48-android-ordinary-part-recovery.md): 313 selected device cases, 39 JVM tests, debug/unsigned release builds and lint with zero errors. Physical-network execution remains prepared for the user to run after implementation. The [completion audit](completion.md) keeps the full application objective active.
