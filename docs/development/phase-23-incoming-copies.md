# Incoming file copies: Android sender and Windows receiver

This increment implements phone-initiated copying into an owner-approved Windows location, including receive-only inboxes. The later [reverse-upload increment](phase-24-reverse-uploads.md) adds a Windows sender and Android receiver; verification below records this increment's original scope. Existing receiving/download workflows in both directions continue to exist. This is progress toward the [full application](completion.md), not a completion or release claim.

## User workflow

1. Pair normally. On Windows, approve a generated-data destination for that phone in **Shared locations**. The permission editor now enables **Receive new file copies** and provides **Read only**, **Contribute** and **Receive-only inbox** choices. Receiving requires both Write and Create; the default remains read-only. Replacement remains unavailable.
2. On Android, open **On this phone**, choose a local-folder shortcut, open it and select **Prepare to send to computer** beneath a file. Keep this view and the app open until preparation finishes. This creates a private snapshot with a complete SHA-256; it does not create a remote phone-storage grant. The original source is kept.
3. Return to Devices, establish a mutually authenticated connection and find **Send into a computer folder**. Use **Load approved receiving locations**, then select the owner-approved location. A Contribute grant can alternatively be opened through the remote browser; explicitly clear a selected receiving location to use that open browser folder. Receive-only locations need no browsing or read permission.
4. Optionally change the receiving filename before its first request. Choose **Send to selected computer destination**. Existing files are kept. Contribute copies use a numbered name on collision; receive-only inboxes always add a random suffix. Wait for the receiver's verified-publication receipt. Windows shows the copy in **Transfers**, including progress, outcome and its local destination.
5. Pause deliberately or leave Android's foreground to stop this sending work. Reopen, reconnect to the same pairing and use **Resume / check receiver receipt**. Saved queues never start these sends automatically. Resume uses the existing incoming ID/context; it does not silently create a new receiver copy after an uncertain response.
6. **Prepare another receiver copy…** is an explicit new-copy decision. Its dialog warns that an earlier copy may already exist. **Remove private send copy…** stops local sending and removes only the app's private snapshot/record after confirmation. It keeps the original source and any receiver copies, including an uncertain incoming partial. It is not a remote undo.
7. On a live pairing with a compatible Windows receiver, choose **Verify published copy…** from a completed Android send. The result applies to that send's recorded Windows file. Android shows the result for the fresh check and keeps the original, snapshot and send receipt.

Windows can **Stop and discard this incoming partial…** after owner confirmation. That operation cancels verification, blocks further writes for that receipt and removes only the identified unpublished partial. It still works after the peer's grant is revoked, using local owner authority and the saved destination/temporary identities. Published files are kept. An uncertain publication must be reconciled or reviewed before cleanup.

**Archive / reset incoming-copy history…** pauses Windows availability, waits for verification to stop and preserves the whole private receipt directory through a handle-relative rename. It creates a fresh incoming epoch. Partial and published files stay in their destinations. Earlier sends lose automatic lookup and require a deliberate decision after reviewing existing copies. It also resets receipt reservations; only the local owner can perform this action. Preserved-metadata cleanup checks bounded, recognized metadata names and keeps unexpected entries. Android's damaged outgoing-metadata archive similarly preserves snapshots; separately confirmed orphan-snapshot cleanup removes only unreferenced private copies, never provider documents.

## Protocol and authority

The optional `uploads-v1` direct-channel capability adds incoming context, preparation, status, bounded write, finish, cancel and paged-receipt operations. New protobuf fields carry descriptors/content and receipts. These messages travel over the existing authenticated file RPC channel; the coordinator never receives upload bytes or destination paths. Android checks receiver support before sending. It does not advertise itself as an upload receiver in this increment.

The receiver's context contains a fresh epoch and up to 32 currently approved receiving roots. Each root has an opaque session reference. A write/create-only root can be disclosed as a receiving location without granting List or Read. For those roots, timestamps and version values do not disclose directory activity. The existing listing/metadata/read/download operations still enforce their own independent permissions.

Each client-created incoming ID contains its creation time and fresh randomness. New/prepared/writing/finishing requests must use the current epoch and the existing 24-hour / five-minute-skew mutation-ID window. The receiver stores the complete intended descriptor, owner scope, peer, grant, volume/root identity, exact destination ancestors/identity and a separately generated private temporary ID before creating a file. Reusing an ID for a different descriptor or destination is rejected. Requests from another peer cannot inspect its receipt. Owner reset and receipt-history reset prevent old contexts from authorizing new effects.

Every content change and publication checks current owner scope, peer-specific Write/Create permissions, grant expiry, exclusions, private-profile protection, volume identity and the exact destination. Access uses the existing handle-relative Windows primitives. Temporary files use create-new disposition and unpredictable reserved names, and identity/single-link/reparse checks prevent substitution or hard-link aliases. Remote cancel can remove only that peer's identified unpublished temporary file under a current grant; it cannot delete a published or arbitrary file. The separate local-owner discard API is never exposed through the RPC protocol.

Writes use sequential ranges of at most 32 KiB. Each acknowledged checkpoint follows a file flush and an atomic synced journal commit. Duplicate acknowledged ranges must match the retained bytes; changed/overlapping/out-of-order ranges fail. After restart, the prefix hash chain is checked before continuing. Extra bytes not covered by a durable checkpoint are truncated only in the identified temporary file. Failed saves block further incoming work in that runtime and keep the earlier checkpoint for reviewed/cold recovery.

Finish launches one of at most two verification workers. Workers reread and hash the retained file, checking authority at read boundaries and immediately before publication. Handles deny concurrent mutation while verification/publication runs. Publication writes intent first and uses no-replace rename; keep-both/skip/fail outcomes remain distinct. A repeated finish reconciles an uncertain final name using the same file identity and complete checksum, rather than creating another copy. Permission changes after the final intent are checked again before the filesystem effect. Verification failure exposes review; it does not mark a checksum mismatch complete or poll forever as healthy work.

The optional `published-upload-check-v1` capability lets a sender request a fresh check for an exact completed receipt. Windows checks current receiving authority, durable receipt data and the recorded attachment-check policy version. It opens the recorded destination by native identity and rehashes the bytes with the existing verification limit. Windows keeps handles open against replacement and writes until the short-lived proof is collected, the session or grant ends, or the proof expires. The challenge and result are bound to the active authenticated session. This check uses the recorded attachment-check outcome and does not rerun the scanner. [Manual validation step 59](physical-network-validation.md) covers separate networks and changed copies.

Limits are 128 receiver receipts overall, 32 per peer, 16 GiB per peer and 64 GiB overall of pending reservations plus completed receipts retained within the ID window. These are not a lifetime disk-space quota or configurable bandwidth policy. Active/uncertain records are not silently pruned when old; the owner must review/cancel/archive them. Normal terminal receipts expire from the catalog only when a new preparation can safely prune them outside the replay window. The generic RPC's bounded credits/queue/frame limits also apply.

Android allows up to eight retained private snapshots sharing a 16 GiB reservation, including partials/orphans. Snapshots use generated private filenames, no-follow/exclusive creation, inode/device/single-link checks, complete source metadata/range validation and SHA-256. The sending stream rechecks the private snapshot before contacting the receiver. Records bind the local identity, pinned peer and pairing epoch. Original provider paths/URIs are not put into these outgoing records. Local browser cancellation invalidates captured readers; app backgrounding cancels these sends. Selected background-transfer authorization for the older download/source-ticket paths cannot authorize an upload.

## Evidence and remaining work

Fifteen new Windows tests exercise real NTFS files: partial restart/resume, repeated/changing ranges, missing permissions and wrong peer/epoch, descriptor reuse, revocation and local cleanup, prefix corruption, empty files, whole-hash mismatch, keep-both/skip/fail, quota/substitution denial, checkpoint failure, lost publication receipt, owner reset, blind-inbox privacy, late permission changes and explicit history rotation. The existing native authenticated WebRTC RPC test now transfers a 256 KiB-plus incoming copy and verifies actual destination bytes. It uses in-process native peers, not an external coordinator or Android phone.

Android adds descriptor/capability JVM tests and device tests using a real generated local provider, local browser and private snapshots. Scripted receiver replies deliberately lose an accepted-range acknowledgement, validate resumed bytes after a sender restart, refuse changed pairing/foreground access, reject corrupted snapshots before a network request and preserve source files across damaged-metadata/orphan cleanup. Scripted replies do not prove Windows–Android interoperability. Native component UI coverage exercises local snapshot preparation without creating remote sharing.

The full .NET Release build has zero warnings/errors, and all 215 tests pass (207 core/storage/connectivity/model/coordinator tests plus eight native preview tests). Android debug app/test and unsigned release APK builds succeed. All 20 JVM tests pass. After installing and verifying the final debug APK's SHA-256 (`14d313c3256a439e12deb0da0d679de21f3634ed3ae35af7efa0c35e22cab9f3`), all 99 emulator device/UI tests pass in 136.479 seconds. This includes the four new outgoing-copy tests. Lint reports zero errors and 44 existing advisories. The owned test emulator is stopped afterward. `git diff --check` passes; changes remain uncommitted and new files are included through intent-to-add for review. No commit, push or deployment is made.

Remaining requirements include the Windows-initiated/Android-receiver path, outgoing folders/batches, selected upload background execution if added, receipt/archive import and complete uncertain/absent-location recovery, large-file/disk-pressure/concurrency/provider and physical-device coverage, final native/accessibility UI review, production quota/bandwidth controls, origin/security metadata and scanning behavior, packaging and independent security review. An SHA-256 match establishes byte integrity, not that a file is safe. Fresh Windows–Android upload interoperability is still unverified; the earlier coordinator-launch approval rejection has not been retried through another launcher.
