# Fresh checks of completed received batches

Windows and Android receivers implement `VERIFY_PUBLISHED_BATCH` (operation 46), negotiated separately as `published-batch-check-v1`. Both senders expose **Verify saved batch** for a completed, fully successful send when the original paired receiver advertises this capability. Existing peers can continue using their earlier batch operations.

This checks the destination at the time of the request. It leaves original sources, private snapshots, published copies and durable receipts intact. It does not authorize source removal, establish file safety, or complete cross-device folder moves.

## Authority and receipt binding

The request carries its original complete batch header, batch ID, receiver history epoch and a new canonical challenge. It cannot select an individual item, destination, alternate name, upload descriptor, payload or byte range. The receiver requires the original peer and pairing generation, current owner authority, current Write and Create approval, retained detailed history, completed parent phase and a successful outcome for every item. Stopped, partly skipped, source-error, retiring and compacted batches cannot produce a successful check.

Pending and successful responses include the same challenge and completed parent receipt. Both implementations validate the wire response. Senders compare the entire header, history epoch, retained outcomes, challenge and effect barrier before accepting success. An old completion receipt alone is insufficient. A check from another live session or challenge cannot collect the result. Collection consumes the result; polling again starts fresh work after resource release.

## Windows destination check

The worker reads the retained manifest, directory ownership records and each file's scoped publication journal. File records must retain the original native file identity and completed attachment-policy version. Actual published names, including collision and blind-inbox names, determine the paths; manifest names never adopt a replacement destination.

The original destination root and parent identities are checked. Items open in manifest parent order, keeping at most the bounded manifest's 4,096 destination handles plus the root chain. Files must retain their native identities, regular single-link metadata, recorded lengths and SHA-256 values. Files remain open without sharing writes or deletion until collection or expiry. Directory membership must exactly match the batch's actual saved child names and kinds, including empty folders. Unrelated objects in the approved destination root are permitted; additions inside a created batch folder fail the check.

Before returning success, the receiver checks current authority again, validates private context and receipt versions, rechecks access to every saved path and enumerates created folders again. No response returns file contents or local paths. The two existing incoming-verification slots are shared with ordinary and batch file publication. Work and collection share a ten-minute-plus-thirty-second deadline; a finished result has at most thirty seconds for collection. Senders stop polling after ten minutes. Scope closure, permission changes and verification pause cancel the check. History archival and item retirement wait for its worker to release resources.

Stopping the sender's wait cancels local polling. Disconnecting ends the receiver's session scope. If the session stays connected, an in-flight receiver check can remain busy until its existing deadline or collection expiry, or until the receiver pauses verification. Explicit per-challenge remote cancellation remains a follow-up. A second challenge cannot take over that outstanding result.

Private metadata still relies on the established local owner boundary. This is a point-in-time observation, not a cross-device atomic transaction or a promise that destination contents can never change afterward. Provider validation and a source-recovery transaction remain required before folder moves can be offered.

## Android provider check

The Android receiver retains the same header, pairing, approval, outcome, challenge and session requirements. It opens only the provider document IDs retained by the original directory and file receipts. Actual saved names and parent chains determine the expected graph. Every created folder must have exactly its recorded children; unrelated objects in the selected receiving root remain permitted. Both original manifest names and saved names must remain visible under current policy.

Each file must be a seekable, regular, single-link native descriptor of the recorded length. The receiver streams SHA-256 with native metadata checks before and after reading. Provider names, kinds, flags, sizes and modification metadata must remain stable around that work. At collection it validates the graph again, reopens each file to compare native identity/size/time metadata with the hashed descriptor, then checks the graph once more. It rechecks private receipt versions and current authority before returning success. No published content or private history is rewritten. Uncommitted private metadata is refused before AtomicFile reads can restore a backup.

Descriptors are processed one at a time rather than retaining a handle for every batch item. Providers whose descriptors change between opens, are virtual/nonseekable, or cannot satisfy these checks can refuse verification. Provider IDs and ancestry depend on the selected provider's documented behavior; this does not make a malicious provider trustworthy or create an atomic provider namespace. Android descriptors do not supply Windows sharing locks. Source removal remains a separate unimplemented folder-move transaction.

The existing two incoming-verification slots cover hashing and the thirty-second collection window. Background work has a ten-minute cancellation deadline. Cancellation signals cover provider queries and descriptor opening, with descriptor closure on canceled reads. Session suspension, grant edits, scope closure, history reset and shutdown cancel work. A collection deadline can interrupt its provider query before waiting for the owner gate, and detailed retirement refuses active checks.

Six provider-backed instrumentation methods pass fourteen receiver scenarios: ordinary and blind collision names; changed bytes, names, membership, IDs and parentage; changes triggered at collection; current authority, shared slots and scope withdrawal; private-backup preservation and retirement; and cancellation of a blocked provider read. A seventh passing case checks sender challenge/parent validation and cancellation. The blocked-read case initially exposed an opening path that did not deliver the cancellation signal to the provider. Verification now opens the actual document through a provider client, and the test requires the provider to receive a signal and release its worker within three seconds of session suspension. The final run passes all seven cases without failures or skips. All 58 selected existing incoming-upload, batch-admission and batch-file cases also pass on the same installed APKs; three separate maximum-capacity cases remain excluded from that selection.

The native Windows and Android batch probes now require and execute a fresh whole-batch check before reporting successful sending. A first cross-platform trial completes both transfers and both fresh checks, then fails because Android observes a closed session at the post-withdrawal refusal check. This is incomplete matrix evidence; its cause remains under investigation. The earlier frozen native matrix does not cover the added fresh-check behavior.

## Manual journey

1. Pair the devices and approve an incoming folder on the receiving device. Use an account-owned disposable dataset with nested folders, an empty folder, a zero-byte file and a Unicode filename. Complete a batch send in each Windows–Android direction.
2. In **Batch queue and saved history**, choose **Verify saved batch** on the completed send. Confirm the reported success, then compare all source and destination hashes. Originals and saved history must remain intact.
3. Add an owner file inside a created batch folder, then check again. The check must refuse and preserve that file. Repeat with changed bytes, an identical-byte replacement, a missing empty folder and withdrawn receiving permission.
4. Stop waiting for an active check, disconnect, and reconnect. No old result may be accepted from the earlier session; a new check must begin under the current pairing and approval.
5. Repeat with a blind Write/Create inbox and a pre-existing root-name collision. Verify actual receipt names, keyboard focus, cancellation, screen-reader status and both native controller lifecycles. Record the exact builds and results.

The user's physical mobile-data/separate-Windows-network test remains a prepared field-validation requirement. None of the local checks substitutes for it.
