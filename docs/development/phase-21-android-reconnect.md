# Android foreground reconnect and saved pause

Android now offers **Reconnect to this computer while the app is open**. It is off by default and requires a currently approved pairing and valid coordinator/STUN settings. The saved intent is bound to the phone identity, peer ID, exact pairing epoch and selected endpoints. A changed pairing, identity or endpoint does not inherit that approval. Enabling saves the endpoint before committing the reconnect record.

**Disconnect and pause** and **Pause connections** immediately end current availability and block automatic attempts, then persist a pause marker. **Cancel direct connection** / **Disconnect from computer** also pause retries and reject new peer offers while keeping the coordinator connected. A manual Connect is a deliberate one-off action; it does not clear the saved automatic pause. **Resume automatic connections** explicitly clears that pause after committing current intent. Turning the reconnect switch off stops retries without revoking trust or deleting copies.

Editing a disconnected endpoint pauses existing automatic intent. Revocation/reset blocks it before asynchronous persistence, and re-pairing requires new opt-in. A failed metadata save blocks retries in the current runtime and reports the failure. The pause marker wins even if the subsequent options write fails; any base/backup/uncommitted pause entry blocks cold-start retry. If storage cannot commit any pause intent at all, the current runtime remains blocked but a later launch cannot prove the unsaved action. That failure is visible and still requires storage/power-loss lifecycle validation.

## Scheduling and lifecycle

One foreground coroutine owns retries. A coordinator attempt uses the existing signed registration; an online coordinator can hand off once to the pinned peer. Native authentication, readiness and file authority checks are unchanged. The loop never resumes file or folder queues automatically. Failed connections use monotonic exponential delays with jitter, capped at 60 seconds; pending coordinator/session attempts and pairing cannot overlap retries. Network or foreground flapping does not reset backoff. Only a connection stable for 30 seconds clears the failure budget. Idle coordinator contexts rotate before the replay/session counters fill.

One default-network callback exists while the activity is visible. It uses the ordered callback arguments, tracks the current default network and the UID's blocked status, and ignores stale events after stop. It does not synchronously query capabilities from a callback. An available internet-capable network can be tried even when OS internet validation is absent, which avoids dropping a healthy local direct connection solely because validation changes. TLS/coordinator failures remain bounded connection failures. Android documents these callback/lifecycle rules in [Read network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state) and [NetworkCallback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback).

Leaving the activity cancels the loop and unregisters the callback. The existing explicitly selected notification-backed transfer may continue on its original session; reconnect never creates background authority, a new background session, a boot receiver or a sticky service. A network change during owner-enabled foreground availability closes the old session and pauses work before retry. Disconnect cancels pending WebSocket establishment as well as open sockets, rather than leaving a handshake queued after the foreground lifetime ends.

## Private state and recovery

The bounded private record lives in `files/availability/reconnect.json` (8 KiB maximum); the pause marker is separately committed. Strict schema/types, phone identity, pairing epoch and canonical endpoints are checked before automatic use. Main-thread revision changes invalidate an in-flight enable immediately; a late I/O completion cannot publish an old permit. Writes use the existing synced/read-back AtomicFile wrapper on the I/O dispatcher. No record grants file access or substitutes for current owner policy.

If these settings are damaged, **Reset automatic connection settings… → Preserve and reset** moves the whole earlier metadata directory into a private local archive and writes disabled/paused defaults. Unexpected pause entries are preserved with it. Pairing, storage approvals, provider documents, partials and copied files are separate and kept. Preserved directories are capped at 32; archive export/review/cleanup and capacity UX remain required release work. Complete same-key authority/intent rollback cannot be detected without an external monotonic checkpoint; backup/restore and independent review remain open gates.

## Verification

- Four JVM schedule tests pass: bounded/jittered monotonic delays, no overlap, foreground/network/consent flapping, stable-authentication reset, one coordinator handoff and idle-only refresh. The JVM suite now has 14 cases.
- Six real-device policy tests pass: default off, exact target/identity/epoch binding, cold reload, committed pause despite a later options-write failure, in-flight enable cancellation, malformed/oversized/uncommitted settings, failed pause removal and metadata-preserving reset.
- The controller fixture uses a real mutually approved test pairing, isolated private state and actual refused loopback WebSocket attempts. It verifies opt-in, saved pause, a one-off manual attempt, explicit resume, foreground stop/return, endpoint edits and revocation. The network notification source is an injected test adapter; production uses ConnectivityManager. It starts no coordinator or external service.
- Final device/UI regression: `OK (94 tests)` in 115.244 seconds, including all seven reconnect cases and the prior connection, native authentication, storage, recovery, explorer, lifecycle and isolated-preview cases. Fourteen JVM tests pass. Debug/test APKs and the unsigned release APK build successfully; CI now compiles all three variants as well as running JVM rules and lint. Lint reports zero errors and 43 advisories; the extra KTX-style suggestion accompanies an intentionally synchronous, checked preferences commit on the I/O dispatcher. The prior .NET baseline remains 192 passing tests; this phase changes Android code only.

Successful Windows–Android reconnect, real coordinator restart/outage recovery, restrictive/independent networks, actual OS network transitions, hardware/process-death/force-stop, full native settings/accessibility flows, background selected-transfer coexistence, archive capacity/cleanup and release signing still need evidence. The local coordinator launch was rejected by automatic approval review in phase 20; it has not been restarted through another route. These tests do not prove that missing integration gate. The operator's separate-network kit remains prepared for after implementation, and the full-application goal remains active.
