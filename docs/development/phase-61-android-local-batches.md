# Android local file and folder batches

Android can plan and copy selected files and folders without pairing, a coordinator or sharing approval. Local source selections become a separate copy purpose with read-only provider-access leases. Removing the browsing shortcut does not silently revoke access needed by a retained plan. The destination uses Android's actual folder picker and its own retained receiving access.

## Source planning and access

`PhoneLocalBatches` owns separate source, receiving and parent-batch stores. Its private source adapter accepts only the empty local owner; ordinary batch receivers still require paired-device fingerprints and epochs. This is not a synthetic peer or a new network file host. The local browser's RPC whitelist is unchanged. Batch-only file receiving rejects standalone file receipts.

Plans include selected folders, nested/empty folders and zero-byte files. Bounds are 128 selected roots, 32 distinct provider trees, 4,096 items, 32 relative components, 2,048 path characters, a 4 MiB transfer manifest and an 8 MiB source journal. Eight retained contexts and 16 GiB of declared source sizes bound admission. These are not app-wide quota or capacity-performance claims. Overlapping provider document IDs, conflicting top-level names, excessive trees and source changes during scanning abort planning without publishing a partial draft. Unsupported virtual/unknown-size children are explicit source issues; unsafe names abort planning.

Provider document IDs, names, types, file versions and sizes form a frozen selection. Later-added documents are excluded. Listings and roots are paged; the shared Android resolver now follows root continuations while rejecting ambiguity. The source adapter exposes only planned nodes; a selected file cannot list unselected siblings. Bounded range reads, prepared SHA-256 and source checks feed the existing verified receiver.

This is a frozen selection of provider documents, not a private snapshot of all original bytes. Change detection depends on the provider's stable document IDs and reported size/modification data. A provider with coarse or misleading metadata limits what can be detected before hashing. Provider ancestry/access is checked by the existing SAF boundary; these tests do not prove every physical/cloud provider's behavior.

## Destination, lifetime and recovery

Destination approval first retains offered read/write access, then validates the provider and rejects a known destination inside a selected source folder. Only afterward does the source journal durably record that copies may exist and the receiver begin. The source cannot choose another fresh destination after receiving history is lost. Removing missing references requires a separate review and removal of associated file receipts. Restoring older coordinated private metadata and full-profile rollback remain separate requirements.

Folder creation never merges or replaces an existing folder. Keep-both, skip and fail apply to conflicting items or folder branches. Files use bounded private staging, checkpoint verification, SHA-256 and provider read-back. Uncertain folder creation requires an explicit branch skip; uncertain file saves require checking an earlier recorded copy or explicit additional-copy review. Existing and uncertain provider objects stay intact.

Canceling the picker retains the draft. Work pauses outside the foreground and waits for explicit resume after restart. Shared foreground/cancellation checks prevent a canceled worker from dispatching receiving or publication after the app returns. Closing cancels workers and waits before closing queues. If cancellation arrives after a source draft was committed, its retained purpose keeps provider access.

The native page provides multi-selection, planning cancellation, destination review, 20-item pages, progress, pause/resume, uncertain-save/folder reviews, cancellation and record removal. Separate unattached-receipt controls cannot fetch source bytes or create a new provider copy: they stop private staging, check an already recorded provider copy, or remove finished progress. Metadata preservation/removal keeps originals, provider objects and private staging. Whole-store/orphan payload recovery and complete history workflows remain in the completion audit.

Cloud-backed providers may use the internet; the review explains that local copying does not promise offline provider behavior. No new remote approval, pairing or coordinator registration is created. Activity continues through fixed local-copy observations rather than source paths, document IDs or URIs.
