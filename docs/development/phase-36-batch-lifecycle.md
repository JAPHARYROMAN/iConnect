# Receiver batch stop and completion

Both receiver implementations now have explicit stop and completion operations. These are receiver primitives for the forthcoming native sending queues; `upload-batches-v1` remains unadvertised.

`FINISH_UPLOAD_BATCH` binds to the original batch ID and history namespace. It requires the accepted manifest, no active file verification and durable final receipts for every usable item. Source errors count as failed items. A skipped or failed directory suppresses its descendants without creating them. Pending or uncertain items prevent completion. The receiver checks that identified private file staging is absent before committing completion and releasing the batch's byte reservation.

`STOP_UPLOAD_BATCH` cancels an unstarted plan through its existing canceled receipt. For a started plan, it first commits a stopping barrier. The receiver then refuses new child effects and invalidates earlier worker scopes. Windows commits this barrier before canceling verification. Android also has a reversible fast pause for an already-bound worker matching the authenticated peer, batch and namespace: a blocked provider operation must be canceled before its owner gate or provider queries can become available. Durable stop still requires the full authorization checks and committed barrier; that early pause neither deletes data nor acknowledges completion.

Stopping never waits for asynchronous workers while holding the parent lock. A request can return stopping until those workers quiesce. Subsequent requests remove only identified private partials. A saved cleanup cursor prevents every retry from rereading the entire child inventory: each request scans at most 256 items and cleans at most 16 files. Cancellation or a lost reply can repeat this work through the same ownership receipts and cursor. Created folders, completed files and possible provider publications are preserved. An uncertain published item has a review outcome even when its private staging can be removed safely.

Only after worker quiescence and private-part accounting does the receiver persist stopped outcomes and release its byte reservation. The complete outcome array is bounded to one phase byte per manifest item. Completed plans cannot contain pending or review outcomes; stopped plans distinguish unprocessed, succeeded, skipped, failed and review items. Terminal status and child receipt reads remain available through the original authority checks. Terminal plans cannot be resumed, resealed or changed into a fresh copy by replaying their identifiers. New copies need deliberate new intents.

Parent metadata now uses schema 2, preserving the canonical accepted manifest, cleanup cursor and terminal outcomes. Known schema-1 admission records can still load. An older reader refuses schema 2 instead of ignoring stop state. Cold startup compares terminal outcomes with retained child receipts. Current peer/pairing, grant, destination identity and exclusion checks remain in force. Android releases its per-batch SAF job lease after terminal state is committed and reconciles terminal history without reacquiring that job lease.

The existing eight retained plan records, per-peer history bounds and metadata limits remain. Terminal transitions release byte reservations; per-plan retirement/history controls and active-slot/history separation remain unfinished. Complete sender intents, native queue/recovery controls and fresh cross-platform/release/physical-network evidence are still required. These primitives do not establish full outgoing batch sending.

## Verification

The first targeted Windows run found a test assumption that Stop must return stopping before returning stopped. Cancellation can quiesce synchronously. The test now captures the persisted parent state from the cancellation callback to verify the barrier, and accepts either valid response state. A subsequent selected run passes 16 cases, including the new lifecycle cases and earlier stop/resource checks.

The Windows solution builds with zero warnings and errors. The final main regression passes **355 tests in 1 minute 28 seconds**, including all eight lifecycle cases and the terminal-receipt contract check. The separate receiver-capacity case passes **one 4,096-item / 4,095-file test in 8 minutes 55 seconds**, including actual three-byte file publication, parent completion, released byte reservations, manager reopening and terminal receipt replay. That capacity fixture uses an injected accepting attachment checker; it does not establish 4,095 actual native attachment checks. All **eight isolated preview tests** pass in **nine seconds**. The unchanged private-source capacity case was not repeated in this phase.

Android debug, instrumentation and unsigned release packaging pass, with **39 JVM tests**, **zero lint errors and 67 advisories**. Review found that cancellation inside the batch handler could still wait behind the file service's outer owner lock. The fast pause now runs before both service and owner locks, matching only an existing worker's peer, batch, namespace and optional original header. An instrumentation case explicitly holds the owner lock while requiring a blocked provider open to observe cancellation; that case passes separately in **21.447 seconds**.

The first receiver run passed 31 of 32 cases. Its failure expected a plan lookup error for an unapproved peer, while Android correctly denied that peer at the earlier authorization boundary. Only that test assertion changed. The final broader regression then passes **204 device tests in 190.626 seconds**, including all 32 receiver cases, native screens, ordinary transfers, trust/revocation, previews, lifecycle and saved-progress recovery. It excludes four live-invitation classes and four separately tracked capacity cases. Installed APK hashes match the build outputs.

The separate Android staging/stop capacity case passes in **2,836.27 seconds** (47 minutes 16 seconds). It prepares **4,095 actual private parts** in a 4,096-item plan, reopens them with one batch job lease, then repeatedly stops through the saved bounded cursor. It checks monotonic progress, private-part removal, released byte reservation and job lease, preserved provider directories, descriptor closure and cold terminal replay. The measured duration leaves staging/cleanup performance as an explicit remaining concern; the test does not provide a separate timing breakdown. This pass proves correctness through the fixture provider, not acceptable production throughput.

The separate full publication/completion case passes in **525.444 seconds** (8 minutes 45 seconds) on the same app and final test APKs: **128 actual provider folders and 3,968 actual three-byte files** form a 4,096-item plan. All files publish and verify; the parent completes with 4,096 final outcomes and releases its byte reservation. Reopening validates terminal history and replays the completed parent and final file receipt. The owned emulator was stopped after rechecking its AVD identity and both installed APK hashes. The existing Windows desktop fixture was not controlled or replaced.
