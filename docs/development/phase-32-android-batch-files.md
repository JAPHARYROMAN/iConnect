# Android scoped batch files

Android now stages and publishes file children inside an accepted outgoing batch plan. The receiver derives each file's descriptor and destination from the original validated manifest and its retained directory receipts. Operations 39–42 prepare, write, finish and cancel that child; item status (38) dispatches by the manifest's recorded kind. The optional `upload-batches-v1` capability remains unadvertised until private source preparation, sending queues and recovery controls are complete on both platforms.

## Ownership and publication

The parent records a deterministic file-child binding and attempt bit before creating a one-row incoming journal. A fresh scope never saves an empty journal. Once the attempt begins, a missing binding, index or journal requires local review; retry cannot create another copy. Cold startup binds every retained journal to its original owner, peer, pairing generation, parent history epoch, manifest descriptor and provider ancestor IDs/names. Orphaned journals and externally changed metadata block new incoming work. The ordinary upload path still rejects the batch child's reserved identifier form.

The existing incoming engine receives bounded ranges into an app-private part, flushes checkpoints, validates repeated ranges and the retained prefix chain, then checks whole-file SHA-256. Publication creates a new provider document, durably records its returned URI, requires an empty regular single-link seekable descriptor, writes and syncs bytes, and reads them back before completion. It never overwrites or adopts an existing provider document. A lost creation result, renamed document, changed parent, unsupported descriptor or interrupted publication preserves copies for review. Retrying a recorded provider copy verifies it without rewriting it. Integrity verification does not establish that received content is safe to open.

Current grants, exclusions, framework read/write access and pairing generation remain mandatory. Receive-only destinations use unpredictable new names and expose only the peer's retained receipts. Owner-created destination files do not change an already completed receipt. Neither receiving a batch nor retaining a receipt grants remote browsing permission.

Closing the originating session or leaving the Android foreground immediately cancels batch verification, including when an unrelated explicit single-file background job preserves the session. Batch work cannot inherit that background authorization. The provider-open helper also closes a descriptor returned after cancellation, avoiding a late-open descriptor leak. Verification-slot cleanup covers cancellation before a lazy coroutine starts as well as its normal completion paths.

Monitoring the first file-capacity attempt exposed a separate leak: **8,145 private-part descriptors**, including deleted parts, remained open after more than 2,600 files had been published. Android's [stream constructor borrows an existing descriptor](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/android-30/+/refs/heads/main/java/io/FileInputStream.java); closing that stream does not transfer the `Os.open` caller's ownership. All seven raw-open sites in incoming receiving, scoped/ordinary orphan cleanup and private single-file sending now close the owned OS descriptor in `finally`. Framework-owned provider descriptors keep their separate `ParcelFileDescriptor` lifecycle. The owned instrumentation process was stopped after this concrete finding, not because the test exceeded a time estimate. That run is interrupted evidence and is not a capacity pass.

## Bounds and local recovery

The parent owns the logical aggregate reservation. Prepared file children do not charge it again or consume standalone receipt slots. Physical private-storage admission accounts for unwritten bytes across ordinary incoming files and prepared batch children, leaving a 64 MiB margin. It reserves private bytes as children are prepared, allowing sequential processing without allocating the entire declared batch at admission.

Ordinary and scoped incoming files share two verification permits. The batch host caches two idle/active receiver objects and can open a transient status-only receiver when both are busy. Each batch retains one SAF access-registry lease rather than one per file. The private part directory has one process lock; child managers do not retain thousands of file-lock descriptors. All ancestor and provider identity checks still execute for actual effects.

Flat file journals are bounded to 256 KiB each and 16 MiB per batch. The separate child-binding budget, eight-plan / four-per-peer limits, 4,096-item manifest limit and shared incoming-byte quotas remain. Metadata-heavy paths can exhaust the journal budget before the item limit; the receiver refuses further preparation rather than losing ownership records. Native inode/length/high-resolution modification/change timestamps detect missing or externally changed journal files before cached state is reused. Directory-version caching avoids a complete private-part scan after every owned creation.

Private parts live outside metadata archives. Owner archive/reset first pauses and joins verification, preserves old metadata and every provider/private copy, rotates the history namespace, then releases the archived plans' recorded SAF leases. Abandoned private parts appear separately for explicit owner cleanup. Cleanup opens only canonical, unowned, regular single-link part files and checks opened identity before deletion. Damaged ownership must be archived/reviewed before cleanup is available; no remote request removes abandoned owner data. Missing complete metadata while private parts remain blocks automatic history initialization and retains unknown OS access for review.

Parent cancellation after child effects start still requires review and retains its logical reservation. Complete per-plan terminal accounting and native incoming/outgoing queue controls remain part of the sending workflow.

## Verification

The corrected debug/instrumentation/unsigned-release APK builds, **38 JVM tests** and lint pass. Lint reports **zero errors and 63 advisories**. Installed app/test APK SHA-256 values were verified against the build outputs before device testing.

On the corrected build, **28 focused cases pass in 52.125 seconds**, covering 24 scoped cases and all four existing private single-file sending cases. They exercise actual 98,317-byte restart/resume and provider read-back, descriptor/index/kind substitution, ordinary-ID separation, shared verification limits/reservations, current permissions/exclusions/pairing, cancellation, keep-both/skip/fail, receive-only receipts, foreground withdrawal, changed provider parents, checkpoint corruption, missing/corrupt ownership and invalid completed-provider identities. The missing-entire-metadata case verifies that private parts and unknown OS access survive until explicit owner archive/review.

The broader corrected-build regression passes **174 tests in 201.632 seconds**, excluding four live-invitation cases and three separately tracked capacity cases. It includes native Android screens, isolated previews, local-source tickets, lifecycle/reconnect, trust/revocation, ordinary receiving/sending, directory effects, archive/recovery and runtime protocol checks. This is not a claim that every scheduled device case passed in one run.

The private-checkpoint capacity case separately passes in **368.242 seconds**: one directory and **4,095 one-byte file descriptors** prepare 4,095 actual private parts and receipts, retain just **one batch SAF lease**, and reopen the final receiving receipt. No payload bytes are uploaded in this case. Private-part descriptors are asserted closed between groups of operations and after reopening.

The final-build provider-publication capacity case separately passes in **1,794.834 seconds** (29 minutes 55 seconds): **128 directories and 3,968 actual three-byte files**, exactly 4,096 items. Every file is prepared, written, verified and published through the real fixture provider. Each receiving directory is checked for its 31 files. Private parts are gone after completion; reopening validates all retained metadata, recovers the final completed receipt and rereads its actual provider bytes. Descriptor assertions pass between completed groups. Live samples during this run show zero or one active private-part descriptor rather than the earlier accumulation of thousands. This proves the bounded emulator receiver path, not physical-provider or internet interoperability.

The descriptor regression checks ordinary/scoped preparation, writes, publication, orphan cleanup, failed sending and resumed sending. Its resource oracle first verifies that it can observe an intentionally held descriptor. The publication capacity case checks descriptors between completed groups as well. An earlier 18-case run passed 17 cases; its remaining failure was a re-pairing fixture selecting a root after the old pairing lost access. The corrected setup passes in the final runs. Earlier 22-case results precede the raw-descriptor fix and are not the final-build evidence.
