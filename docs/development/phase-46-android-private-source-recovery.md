# Android private batch source recovery

Android now provides owner-reviewed recovery of a blocked private snapshot store. It preserves the complete app-private metadata and payload tree in a sibling archive and opens an empty preparation store. It keeps originals, receiver files and the separate sender records intact. Preserved ownership records are never adopted as live snapshots or replacement sending instructions.

## Preservation and retained controls

The controller pauses preparation and sending and waits for their cleanup callbacks. Source reset admission and confirmation are guarded by the same owner gate as sender work. Active preparation, sender workers and verified source readers prevent preservation. The current local identity must be healthy and the app must be in the foreground.

A single-use review captures the current owner generation, store directory identity, child directory identities, every regular file's native version, byte totals, file/folder counts and unrecognized-entry count. It expires after two minutes on a monotonic clock. Confirmation verifies those identities and the complete inventory again, retains a profile-level lease while releasing the inner store lease, renames the entire directory without replacement, and opens a fresh directory and lease.

The inventory admits the normal two-level layout: regular top-level records and flat snapshot folders containing regular files. Unknown regular files and flat folders are preserved and explicitly counted. Nested folders, symbolic links, hard links, redirected entries, excessive counts and excessive logical byte totals are refused for local investigation. Child files named `owner.lock` are counted as ordinary preserved files; only the live root lease is omitted from the reset dialog's file total.

Retained sender records keep their original receiver headers, attempts, receipts and stop controls when those records and the pairing remain valid. A resumed file send cannot substitute a preserved source for its original live snapshot. The native confirmation explains that the preserved snapshots are no longer available for sending or resuming and that receiver copies may already exist.

## Storage accounting and copy review

Preserved logical file bytes remain charged once to the shared outgoing profile quota and conservatively to every peer's quota, because unreadable ownership cannot safely assign those bytes to a peer. They are already materialized and do not also count as pending writes. The archive inventory is reconstructed from the filesystem at startup, before new batch preparation, and during review and cleanup. Uncertain inventory blocks new outgoing growth. Closing a resource participant retains its reservations until the next owner reopens it.

Before preservation, confirmation creates and syncs an empty, create-only marker outside the live store and archive trees. The marker requires future private batches to retain additional-copy review, including after all source archives have been removed and after app restart. When an older valid source store is restored alone, both platform loaders also raise the flag on its ready snapshots while the independent marker survives. This keeps a restored record's earlier flag from bypassing review. The upgrade retains the original source authority and checksum; a failed commit blocks new outgoing growth. Archive cleanup cannot clear the marker. This does not detect rollback of the complete profile.

## Inspection and separate removal

The native Transfers screen lists up to eight preserved source stores and exposes a local inventory in pages of 50 entries. Permanently removing an archive requires a separate review of its exact remaining files and folders. Unknown entries are counted in that review.

Removal processes at most 64 reviewed files or directories per call in postorder. It checks each file's native version and its original parent directory identity before deletion, and only removes empty directories. New or changed entries stay for fresh review. Reservation accounting is refreshed after actual deletion, including when foreground withdrawal interrupts a call. The native loop yields between calls and ends when its screen is disposed. Current-process progress can be continued explicitly; restart and owner-generation changes require fresh review of the remaining entries. Peer revocation does not prevent local owner cleanup.

Current private snapshots, sender metadata, originals and received files remain outside archive removal. No recovery or cleanup action contacts a receiver or enables sharing.

The first focused device run passed **18 of 19 cases in 21.087 seconds**. The remaining test could not initialize because its Kotlin expression body inferred an exception return value rather than `Unit`, which JUnit requires. Giving that test an explicit `Unit` return type corrected the declaration. The subsequent screen runs reached preservation, then exposed two fixture assumptions: the inventory entry required scrolling, and reopening local folders required an explicit browse action. Those test-only corrections leave the application APK unchanged. The final native screen case passed in **4.491 seconds**. Evidence: `.tools/phase46-android-source-recovery.log`, `.tools/phase46-android-source-ui.log`, `.tools/phase46-android-source-ui2.log`, `.tools/phase46-android-ui-final-build.log`, `.tools/phase46-android-source-ui-final.log`.

The native panel case cancels both dialogs, preserves and inspects the archive, removes only its reviewed snapshots, keeps originals and sender records, and reopens the controller to verify future-copy review without enabling sharing or authentication.

Android uses app-private native filesystem identity checks, no-follow file opens and cooperative profile leases. These do not establish resistance to a hostile process sharing the application UID, full-profile rollback protection, actual process/power-loss durability, or full-capacity review/removal latency. Bounded complete archive inventories are rescanned during review and accounting; largest-store performance remains unproven. The hard-link count guard is present, while this emulator's sandbox previously denied hard-link fixture creation; symbolic-link refusal is tested instead.

This phase also hardens the [Windows private-source loader](phase-45-windows-private-source-recovery.md) for separate source-store restore. Windows UI automation remains stopped following the user's physical Escape. Batch support remains unadvertised. The [physical-network kit](physical-network-validation.md) remains prepared for the user to run after implementation.
