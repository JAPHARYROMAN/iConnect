# Phase 14: Windows background availability

The WinUI process now owns an ordinary-user availability agent that can stay alive in the notification area while its window is hidden. Background mode, sign-in startup and automatic reconnect are separate owner choices, initially disabled. Existing identities, trust and individual storage grants continue to authorize every connection and file request.

## Owner workflow

Configure the coordinator and approve the desired device/storage as usual. In **Settings → Windows background availability**, choose the options and save. **Connect** resumes availability; **Pause availability** ends current access, pauses transfers and stops retries. Pause remains saved across launches. Closing the window in enabled background mode keeps the agent and existing transfers alive. The notification-area menu provides **Open iConnect**, **Pause availability / Connect** and **Quit iConnect**. Settings also provides Quit. Quit drains the current process; configured reconnect may run on a later launch unless paused.

Sign-in startup requires background mode and registers one quoted command for this Windows user/profile. Windows Startup settings can separately disable it. The command includes `--sign-in`: the app rechecks saved startup consent before connecting or hiding. Thus an obsolete Run entry cannot override a successfully saved opt-out. An already-running agent ignores a duplicate sign-in launch. A normal second launch brings its existing window forward.

If the tray or local activation endpoint cannot be established, the window stays visible. A tray-registration failure after an Explorer restart brings the window back. The settings page distinguishes a matching startup entry from a requested option. Unexpected registry values are preserved for explicit Windows-side review.

## Reconnect and authority

Automatic reconnect checks current owner intent, pause markers, configuration, network availability, active handshakes and trust before each attempt. It tries the coordinator, then the last explicitly selected paired identity. Failed attempts use exponential delays capped at 60 seconds. It does not switch to a device based on its display name. Active authenticated sessions and pairing flows are left intact; an idle signaling context can be refreshed after 32 sessions or 1,024 received signals to retain bounded replay bookkeeping. Interrupted transfer queues still require their normal resume/revalidation workflow.

The Windows power-message handler ends live access for suspend/session end and allows configured retry after resume. Logout terminates the ordinary-user process. Hardware sleep/resume, logout and network-change behavior still require field verification. The network-availability signal is a hint, not evidence that a phone or a direct path is reachable.

A source signaling an offline target now receives a session-bound failure if it opted into `Registration.signal_status`. The coordinator validates the signed signal before returning this response. Both clients accept it only for their current session and pinned peer. It ends peer work while preserving the coordinator connection. Android pauses queues and selected background authority. This message conveys failure only; it never authenticates a peer, proves online presence or authorizes file access. Legacy registrations retain their earlier behavior; older coordinators do not provide this optional response.

Revocation establishes an immediate connection barrier and a saved pause before policy cleanup. A failed revoke stays latched against manual/automatic resume in that run, allowing explicit retry. Removing a revoked peer from reconnect preferences cannot skip the remaining queue cleanup. If all relevant storage writes fail, the app reports that saved pause/revocation needs another attempt; it cannot promise a durable change that the OS refused to write.

## Local state and activation

Preferences live in a bounded 16 KiB private `availability/preferences.json`. A separate `pause.json` family is checked on startup, so a committed pause survives a failed preferences update. Resume commits preferences before clearing the pause barrier; failed removal remains paused. Damaged preferences disable automatic/background operation and appear in the existing owner-confirmed recovery UI. Archival preserves metadata and resets optional preferences. These changes share the profile's existing single-owner lock. Earlier CNG identities created from trailing-separator profile paths are retained; conflicting existing aliases require review.

The activation endpoint uses a per-profile/user hashed pipe name, a protected DACL granting the actual current User SID, and a server owner check on the client. The server verifies the client's impersonated User SID. Its fixed exchange is `OPEN`, `OK`, then a read acknowledgment; no path, settings, grant, script, transfer or file command is accepted. The acknowledgment prevents a disconnect from discarding an unread reply. Requests have a two-second server deadline; client retry is bounded to five seconds. Same-user software remains inside the endpoint security boundary. A separate-user/elevation matrix and independent review are still required.

Sign-in registration uses HKCU's Run key, a per-profile value, REG_SZ, fully quoted executable/profile arguments and read-back verification. It refuses a different existing command or value type and enforces Windows' 260-character Run command limit. Registry tests use a newly allocated test branch and never the real Run key. See [Microsoft's Run-key contract](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys).

The notification-area implementation follows [Shell notification-area guidance](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area) and [NOTIFYICONDATA version-4 callbacks](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw). Window hiding retains the live window object using [AppWindow](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow). Pipe security uses [NamedPipeServerStreamAcl](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeserverstreamacl.create).

## Verification and remaining work

The Release solution builds without warnings/errors and all 114 .NET checks pass. Android debug/test APKs and four JVM checks pass; lint reports zero errors and 39 advisories. The full emulator suite passes 75 checks. Actual Windows–Android interoperability also passes: scoped explorers, durable changes, verified file/folder transfers and an Android controller fault test that ignores mismatched failure notices but retires matching peer work while keeping its coordinator connected.

Focused tests cover saved pause after failed writes, failed resume, damaged preference archival, bounded retry, current-trust checks, sleep/network suppression, idle signaling refresh, actual pipe ACL/owner checks, malformed/stalled clients, repeated activation, registry collision/quoting/length rules and legacy path identity. Live Kestrel tests restart the coordinator at the same address and verify reconnect, verify durable pause stops it, and prove an offline peer leaves other coordinator actions available. Signed-signal rejection and legacy protocol behavior are tested. A failed grant-revocation write cannot be bypassed by Resume.

A disposable native fixture opts into background mode without registering sign-in startup. It authenticates automatically, serves approved real file bytes with no visible window, reopens through a second launch with one owner process, continues serving after the window's close button hides it, displays the saved options and exits through native Quit. The fixture's generated CNG key and owned processes are removed afterward. This uses Windows peers; Android interoperability is recorded separately.

Initial parallel activation tests exposed unread reply loss when disconnect followed a pipe write. The read-acknowledgment exchange and bounded retry fix that transition; repeated activation passes in the full suite. Automated registry checks prove the command contract, not an actual Windows sign-in. Native tray context-menu keyboard navigation, Explorer restart, multi-user/elevation behavior, power/session hardware tests, installed upgrade/uninstall, branding, signed distribution, physical phones/providers, independent-network operation and security review remain release work. Trusted online presence and Android reconnect remain broader [completion requirements](completion.md).

Automatic approval review blocked the optional native `--sign-in` launch smoke check with “blocked by policy” and no specific reason. That runtime check was left unverified; the real Windows Run key was not changed during this development work.
