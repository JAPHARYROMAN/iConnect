# Local activity history and retention

Both platforms now offer Off, 1-, 7-, 30- and 90-day local activity retention with a hard limit of 500 retained entries. Turning recording off clears active history after owner confirmation and persists that choice. Clearing history, changing retention and preserving unreadable metadata affect activity only; they do not alter files, transfer receipts, pairing or sharing authority. Previously preserved recovery copies remain separate from the active journal; clear/off does not remove those backups.

## Android event history

Android adds a private `local-activity` journal with a regular single-link lease file, native directory identity, checks of the current journal's native version and synced/read-back JSON commits. Loading checks the native version around parsing, rejects trailing data and validates exact fields and integer/string types instead of accepting JSON getter coercions. Entries contain compiled action/outcome kinds, a timestamp, an optional validated peer identity, an optional byte count, an optional compiled file-operation code and a repeat count. Arbitrary descriptions, filenames, paths, URIs, file hashes, pairing codes/tokens, file content and raw exceptions are not accepted into these records.

The controller records selected pairing, revocation, connection and sharing events. The actual serving boundary records accepted requests and refusals/errors after the permission decision, without changing it. Successful range writes/reads and status polling are omitted to avoid a per-chunk journal. Accepted requests do not establish transfer completion. Separate hooks run after durable incoming-file, download, private-copy and batch state commits; they distinguish completion, pause/cancel and review outcomes. In particular, receiving completion is recorded after verified provider publication, rather than when Finish is merely accepted.

A 64-command write-behind queue batches events for approximately 100 ms and performs storage I/O outside authorization/provider locks. Consecutive matching events within a one-second window can be grouped, with bounded counts and byte sums. Queue overflow and storage failures are visible as dropped-event counts or a history issue; logging callbacks cannot grant access or change a receiving operation's result. Graceful controller close drains accepted history commands after transfer work stops. Commands cannot queue behind the close barrier, canceled close callers still complete cleanup, and concurrent close calls wait for the writer to release its lease. Process death or unwriteable storage can lose recent events. This is a bounded local activity view, not a tamper-evident or complete forensic audit.

The native activity card provides 50-entry pages, retention confirmation, cancel/clear and separate unreadable-history preservation/reset. Peer identities remain local; only a short fingerprint is displayed. The former eight transient status strings remain a separate **Recent status** view and are not copied into persisted activity.

## Windows retention and recovery

Windows continues its existing local action history and static descriptions, now with a version-2 envelope containing retention and entries in one atomic commit. Earlier array-format history is accepted and migrated when updated. An older development binary that only understands the array format cannot read this envelope; supported downgrade handling remains a release gate.

Native relative opens, regular/single-link checks, the original profile-directory identity and the expected journal version protect saves. New metadata is created without replacement before atomic commit. Unexpected sidecars or changed/unreadable history stop further history writes and remain preserved. Activity corruption no longer prevents controller initialization. A separate owner-confirmed action preserves the journal/sidecars through the metadata recovery mechanism and opens empty 30-day history. A changed record cannot be archived under an earlier captured decision. Original files and unrelated profile entries remain untouched.

The Activity page exposes retention, recording off, history clear and preserve/reset controls. Windows compilation/model evidence does not replace visual, keyboard or screen-reader validation; Windows UI automation remains stopped following the user's physical Escape.

## Privacy, coverage and remaining work

The diagnostic snapshot adds only retention days, retained-entry counts and a history-review flag; Android also includes its current-run dropped-event count. Activity entries, peer identities, journal errors and descriptions remain excluded from exported diagnostics.

This phase does not close complete operation/security-event auditing. Windows incoming-operation coverage, remaining Android local management/recovery/settings events, dedicated activity-backup management, cancellation/error paths, completeness under sustained traffic, actual process/power-loss, storage/provider matrices and independent review remain open. Neither activity nor diagnostics can authorize a transfer, restore a grant or prove that a file is safe. Retention is enforced on history load and updates; it is not a continuously running deletion service while the app is closed or idle.
