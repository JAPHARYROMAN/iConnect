# Signaling after an ended direct attempt

This phase follows the lifecycle gap recorded in [phase 55](phase-55-android-connection-observations.md). A signed message can be authentic and timely while referring to a direct attempt that has already ended. Handling that message must not call a disposed transport, create another effect under the old ID, or disturb a later authenticated session.

## Windows

The new native regression initially failed all four candidate/answer and replay/unknown-context variants. After an actual unpinned-identity rejection, a fresh signed late frame reached the retained disposed transport. A subsequent coordinator invitation did not arrive. The red run records four failures in 1 minute 40 seconds; the timeout was the lost invitation after the late frame, not native authentication setup. Evidence: `.tools/phase56-windows-red-build.log` and `.tools/phase56-windows-red.log`.

`PeerSession` now exposes an atomically published closed state and has a single disposal gate. `ProofClient` retains ended/unavailable attempt IDs in its existing bounded discarded set, checks the retained closed state before routing, and stops forwarding cached native signals after close. Each incoming frame still passes current peer lookup, complete signal validation and nonce replay/limit checks before the ended-ID decision. Unknown sessions remain errors. Old IDs cannot create another native session or restore file authority. The memory remains bounded by the existing 64-session and 2,048-nonce connection limits; a new coordinator connection resets that context.

The final focused Windows journey adds a genuine successor native session, fresh late packets before and after that successor's authentication, a coordinator invitation with a causal forwarding barrier, and an authenticated bounded file RPC. The successor stays usable. A forged signature is rejected at the actual client validation boundary; replayed nonces and unknown sessions still end the actual coordinator stream. The unavailable-peer case also brings the pinned peer online afterward and verifies that a late packet for its removed attempt leaves the coordinator usable.

The Release solution/WinUI build passes with zero warnings/errors in **11.67 seconds**, followed by **10 focused cases in 2 seconds**. Both signed-offer collision orderings and the existing negative-authentication/cancellation cases pass. The full selected regression passes **504 cases in 3 minutes 37 seconds**, with the same three separately recorded capacity exclusions as phase 54. Production storage/connectivity/model/desktop hashes match before and after regression. Evidence: `.tools/phase56-windows-release-build.log`, `.tools/phase56-windows-release-focused.log`, `.tools/phase56-windows-regression.log` and `.tools/phase56-windows-hashes-{before,after}.txt`.
