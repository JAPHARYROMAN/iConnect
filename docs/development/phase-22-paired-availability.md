# Paired-device availability observations

This increment adds optional coordinator reports to the existing Windows and Android applications. It does not establish full application completion or real-network interoperability of the newer connection/reconnect paths. The [completion ledger](completion.md) remains authoritative about outstanding evidence.

## Owner choice and visible states

**Share availability with paired devices** starts off on both platforms. Enable it in Windows **Settings → Connection**, save, then reconnect. On Android, disconnect, enable the matching switch, wait for saving to finish, then connect. Each device makes its own choice. Both devices must use a supporting coordinator and independently opt in before either can receive a positive report about the other.

The interface distinguishes coordinator disconnection, reports being off, an older coordinator without this feature, unknown availability, a coordinator report of availability, a direct connection attempt, and actual mutually authenticated direct connection. Unknown availability includes an absent device, expired lease, disabled reporting and missing mutual consent. It is not an assertion that the other device is offline. The Connect action remains available regardless of the report; direct path establishment and existing identity/readiness verification still decide whether file operations can begin.

Windows reports while its opted-in coordinator session runs, including owner-enabled notification-area operation. Android reports only while its UI is visible and connections are not paused. Leaving the foreground withdraws reporting even when an explicitly selected transfer retains its existing background session. Ending the direct connection withdraws reporting immediately; a deliberate new direct connection can restart it. No reporting choice starts a background session or resumes a transfer queue.

Android checks its saved preference against the local identity. An invalid optional preference disables reporting and exposes a save-again message. A failed settings write is shown as a failure and leaves the displayed choice unchanged. Windows settings remain disconnected-only and use the existing synced atomic settings writer. Device revocation closes the desktop coordinator session; the connectivity client's separate revoke operation immediately removes its local report and updates its remote scope on the next tick.

## Protocol and privacy boundary

The `registered` Notice advertises `presence-v1` through a new optional repeated field. Older protobuf readers ignore that field; new clients do not send new operations to a coordinator that omits it. Registration remains the existing signed nonce challenge. Presence updates follow on that authenticated WebSocket; they do not add an unsigned pre-registration roster to the challenge response.

`PresenceUpdate` carries a fresh request ID, an enabled bit and a strictly sorted list of at most 128 distinct lowercase device IDs, excluding the sender. Disabled updates must contain no peer IDs. Clients derive the list from their current local pins. The server binds an update to the exact registered connection object, not just the device ID.

The server reports a peer as available only if that peer has a fresh enabled lease and its declared scope contains the caller's authenticated ID. Since the caller's scope is also checked, this is mutual disclosure. Declaring an arbitrary ID cannot enumerate connected devices that have not also consented to that specific authenticated caller. There is no public roster, device-name lookup, last-seen time, file listing or authority token. Names continue to come from local pairing records. The service retains scopes only in bounded memory, clears them on unregister/restart, and prunes expired scopes with its existing five-second reaper. Existing service limits remain 64 concurrent registrations and 240 messages per minute per connection; presence does not introduce an unbounded subscriber queue or fan-out.

Enabled clients renew/poll approximately every ten seconds. Server leases expire at 30 seconds using elapsed-time timestamps. A snapshot echoes only the request's ordered IDs and request ID; the client rejects changed scope and discards superseded replies. Positive observations expire 25 seconds after their request was sent, so a delayed response cannot extend its lifetime. Client loops check expiry every second while running. Disconnect, explicit withdrawal and trust changes clear local observations. A remote change can take a polling interval, or lease plus cached-report expiry during an unobserved failure, to appear. Reports are deliberately approximate, never a liveness or authentication proof.

The coordinator can see the opted-in device relationships and connection timing. TLS protects them in transit, not from that operator. A compromised coordinator can lie about availability or deny service; it still cannot satisfy the existing direct identity/DTLS transcript/readiness checks or create storage grants. Pair-specific opaque discovery capabilities and metadata correlation resistance remain further work. No identity IDs, scopes or report payloads are added to application logs or local action history by this feature.

Elapsed-time implementation references: [.NET TimeProvider](https://learn.microsoft.com/dotnet/api/system.timeprovider) and [Android SystemClock.elapsedRealtime](https://developer.android.com/reference/android/os/SystemClock). These references describe timing primitives, not a certification of the application.

## Verification and remaining evidence

Eight new .NET tests cover request bounds/canonical IDs, disabled scope, expiry from request time, superseded replies, scope substitution, mutual disclosure, unknown/disabled/unlisted targets, server lease expiry, fresh consent after reconnect, connection-object binding, malformed authenticated requests, continued invitation operation and Windows revocation. An actual ProofClient receives a positive report through an in-memory ASP.NET WebSocket, remains unauthenticated and cannot capture a file requester. A failed transport test proves disposal releases the exclusive trust-store lock even after the presence send task faults. These tests do not launch a coordinator process or use an external network.

The final Release solution build has zero warnings/errors. All 200 .NET tests pass: 192 core/storage/connectivity/model/coordinator tests and eight native Windows preview tests. The final regression run completes those projects in 38 and 12 seconds respectively. `git diff --check` passes, all new source/document files are included for review through intent-to-add, and no commit or push is made.

Android adds four JVM tests for the bounded tracker and a device-level controller test using isolated app-private state. The device test covers default-off consent, save failure, cold restart, foreground withdrawal, disabling, identity mismatch and malformed optional preference repair. It starts no coordinator or external network service.

The final Android debug app/test APKs and unsigned release APK build successfully. All 18 JVM tests and all 95 emulator device/UI tests pass; the device run finishes with `OK (95 tests)` in 117.058 seconds. Android lint has zero errors and 44 advisories. The additional advisory recommends a KTX preferences helper; this code intentionally checks the result of `commit()` on the IO dispatcher. No lint safety rule is suppressed. The owned test emulator is stopped afterward. Signing/distribution remains pending.

The physical/separate-network test is prepared in [the operator kit](physical-network-validation.md); it is not run by these tests. Fresh Windows–Android reporting, notification-backed foreground/background transitions with a live coordinator, final native/accessibility UI coverage, service load/outage tests and deployment/privacy review remain release gates. The earlier automatic approval rejection of a local coordinator process launch has not been retried through an alternative launcher; in-memory tests are separately scoped tests.
