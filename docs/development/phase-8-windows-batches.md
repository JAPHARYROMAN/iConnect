# Windows folder and batch receiving

Implemented and verified 3 November 2026 (Africa/Nairobi). This adds Windows receiving of selected files and folders from approved remote storage. Android folder receiving/publication remains unimplemented; the [full completion audit](completion.md) retains that requirement and the other product/release work.

## Planning and source boundaries

The native Windows explorer supports selection boxes and **Copy selected files and folders…**. It scans the selection before writing, then asks the owner to choose a local destination and review counts, size, unavailable items and keep-both/skip/fail decisions. **Open selected item** handles single-folder navigation or single-file preview. A connection-generation check rejects a plan if the active device/session changed before confirmation.

`TransferManifests` builds a local, bounded tree from existing authenticated metadata and directory operations. It validates grant and parent relationships, versions, unique names/IDs and page continuations. Case-insensitive destination collisions and repeated/unrelated entries abort planning. Unsupported destination names and denied branches remain explicit item failures. Planning is limited to 128 selected roots, 4,096 items, 32 source-path components, 256 pages per directory, a 4 MiB serialized manifest and 8 TiB total transferable file bytes. These are resource bounds, not tested throughput/capacity claims.

The manifest stores an approved grant identifier plus discrete source-name components. It never grants a remote path access to a local filesystem. After reconnecting, a resolver obtains fresh session-local references through the same current grant and exact names, then checks the file's planned version and size. Existing prepared files retain their peer/grant-bound source tickets and checksums. Changed or revoked sources cannot be silently substituted. File bytes still use negotiated `downloads-v1`, bounded ranges, private temporary files, checkpoint verification and final SHA-256 read-back. No batch metadata or file data is added to the coordinator or a new upload endpoint.

Directories are checked again after discovery, but this is not an atomic snapshot of an arbitrary provider's whole tree. Each file is independently checked and hashed when prepared. The manifest describes accessible items; it cannot enumerate files hidden by owner exclusions or platform restrictions.

## Destination ownership and outcomes

Windows persists each batch separately, with a creation intent, local directory identities and per-file outcomes. It allows eight saved batches and two batch workers; file work shares the existing receiver's overall two-file limit. Files are scheduled one at a time within a batch. Completed child records are folded into the batch's durable receipt before being removed from the file queue, so a large batch does not need one permanent file-queue slot per item.

Folder creation is relative to a held destination handle and never replaces or merges with an existing folder. Keep both creates a numbered folder; skip/fail leaves that existing branch untouched. Every later child operation opens and checks all recorded destination ancestor identities while holding handles that prevent replacement during the operation. A replaced parent or redirected path is rejected before additional file writes.

The creation intent is saved before the native directory operation. If the app stops after creating a directory but before committing its identity, recovery refuses to adopt that unknown directory. The owner must review it locally and start a new copy; existing or uncertain content is preserved. This intentionally exposes an incomplete operation rather than claiming the directory is owned or repeating an uncertain action automatically.

Every item has an outcome, actual destination name where applicable, checksum for a completed file, and an error when interrupted or unavailable. The batch is **Completed** only if every item completed. **Completed with issues** preserves skipped/failed outcomes, including children of an uncopied folder. The UI exposes all item results in pages of 50, plus current-file progress and aggregate verified bytes. Receipts describe completion at the time of the copy, not a guarantee that a user has never changed the saved files afterward.

Pause ends active child work and retains its durable file checkpoint. Resume requires the same trusted source and checks destination identities again. Cancel drains work and safely cleans only receiver-owned private partial files; completed files and created directories remain. Concurrent cancel calls share the same cleanup, and resume/removal is refused during cleanup. A record cannot be removed while owned child cleanup remains unresolved. Revocation cancels that peer's unfinished batches and retains no automatic resume path.

## Verification

The .NET suite now contains **75 tests**, including 12 new batch cases and an expanded native-controller test. Debug and Release builds have zero warnings/errors. Tests cover nested/empty directories, multiple selected items, keep-both/skip/fail without merging, SHA-256 failure alongside successful siblings, concurrent cancel cleanup, source/receiver restart with an unstarted file, destination-parent replacement, interrupted directory-identity persistence, paged discovery, unsupported names, malformed parents, duplicate names, repeated pages and changed sources. The controller test runs real authenticated native RPC, plans multiple items, saves a file and empty folder, then rejects its old plan after disconnect.

After the final per-item interruption labels and layout changes, the full Debug suite passed **75 / 75**, and the Release batch/controller subset passed **22 / 22**. Interrupted outcomes identify the affected item; an uncertain directory keeps its creation-intent state for owner review.

The Android interoperability fixture passed in **38.622 seconds**. Using the actual Android controller/provider and native Windows transport, `download-phone-folder` copied an approved tree containing an empty folder, `Reports/notes.txt`, `simu.txt` and the previously saved 2,097,169-byte binary. Windows reported **`REAL_PHONE_FOLDER_VERIFIED 6 items 2097225 bytes`**, compared both text documents, checked the empty directory and compared every large-file byte. Normal two-way file receiving and synthetic channel checks also passed in the same run. The deterministic binary SHA-256 remains `2ce3172ab5811f22d8e2d9d45d2c71397e38a636b4a5fd5a09517b7454fb2368`.

Native WinUI checks used disposable pre-pinned fixture identities, not a production auto-approval mode. The explorer's selection/copy action reached the system folder picker. Automation could not finish that picker: input was rejected with `PickerHost.exe` not matching the selected `IConnect.Desktop.exe` window. The picker-confirmation journey is therefore not claimed as verified. A separate `IConnect.DesktopFixture --seed-batch` run generated an actual completed batch through the production engine in its isolated profile. The native app then loaded it offline and correctly showed **4 / 4 items, 0 issues, 84 verified bytes**, disabled running-only controls and all expanded item outcomes. No personal files were used.

Two early combined Debug runs produced intermittent `Interrupted` outcomes in an existing single-file restart test and the new paged batch test. The initial assertions did not retain enough error detail to establish the cause. Stronger failure diagnostics were added. Five focused repetitions, a subsequent full Debug run, a full Release run and three further full Release runs passed. This does not establish a fix for that intermittent issue; investigation remains on the reliability checklist.

To repeat the Android check, follow [interop setup](verification.md#reproduce-the-interoperability-check). After Android reports `SENT`, run `download-phone-folder`, require `REAL_PHONE_FOLDER_VERIFIED`, then run the ordinary `download-phone` and `send` commands and require `BIDIRECTIONAL_VERIFIED` / `OK (1 test)`. The optional empty directory exists only in the test APK fixture.

## Remaining scope

Android receiving needs a corresponding provider-aware manifest, directory creation/publication recovery, durable batch decisions and native multi-select controls. Cross-page selection, source leases expiring during very long batches, queue repair, interrupted-directory review UI, source/provider compatibility, full-load performance and the full disk/crash/power-loss matrix still need work. Batch discovery/copying requires Android foreground availability; no whole-batch background authorization is inferred from individual ticket approval. Physical phones, independent networks, >4 GiB data, packaging/signing, independent security review and the other release gates remain outstanding.
