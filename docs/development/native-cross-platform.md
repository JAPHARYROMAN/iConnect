# Direct native Windows–Android transport fixture

This opt-in fixture checks the production `PeerSession` and `RtcTestSession` implementations together. A Windows console process and explicit Android test instrumentation exchange setup, public identities and native connection descriptions through local control pipes and ADB. The encrypted data channel carries authentication, readiness, file payloads, acknowledgements and file RPC. The fixture starts no coordinator and grants no remote storage access.

Each connection role sends one generated 256 KiB file in each direction. Both endpoints verify the transfer checksum; the driver independently compares each sender's reported digest with the other endpoint's saved-file digest. Both also require a denied roots request with no returned entries or content. Windows checks the actual loaded module's absolute path and SHA-256. Production peers enforce the existing direct-candidate and mutual-readiness rules.

## Prepare and run

Build the Windows fixture with the repository's .NET 10 SDK and build the Android app/test APKs with the configured JDK and Android SDK. Use a disposable emulator with the debug app already installed. Finish other instrumentation before running this probe. The driver refuses a mismatched AVD or an already-running app; stopping an idle fixture app is a separate deliberate step after its previous test has completed.

```powershell
dotnet restore tests/IConnect.NativeInterop.Fixture/IConnect.NativeInterop.Fixture.csproj --locked-mode
dotnet build tests/IConnect.NativeInterop.Fixture/IConnect.NativeInterop.Fixture.csproj -c Release --no-restore
# From apps/android, with the configured JDK and Android SDK:
./gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest --no-daemon
```

From the repository root, select the completed source/notice bundle and the new instrumentation APK containing `NativeTransportProbe`. Supply the SHA-256 of the exact installed production debug APK.

```powershell
./tools/test-native-cross-platform.ps1 -Serial emulator-5568 `
    -ExpectedAvdName iconnect-large-files -NativeBundle $bundleDirectory `
    -TestApk $instrumentationApk -ExpectedApplicationSha256 $installedApplicationHash
```

The driver checks the emulator identity and installed app hash before updating only the test APK. Each Windows role uses a new isolated fixture-output copy with the selected source-built DLL. Control commands enter Android through bounded, sequenced files in one random private probe directory. ADB stdin carries encoded setup data, avoiding shell interpretation and Windows command-line length limits. Synthetic received files are identified by their new transfer names; existing inbox files are preserved.

Reports and process logs are under `.tools/native-cross-platform/<run>/`. A completed `result.json` requires both roles, successful instrumentation and host exits, matching hashes and the expected native payload. Failure preserves logs and stops only processes started for the owned disposable fixture. No Windows application UI is launched.

## Ordinary upload engines: prepared fixture

The driver now accepts `-Suite uploads`. This separately exercises `WindowsUploadSender`/`WindowsUploads` and Android `PhoneUploads`/`AndroidIncomingUploads` through the authenticated native peers. Each direction sends a generated **2,097,169-byte** file. The frame suite remains the default and keeps its original 256 KiB payload and denied-authority checks.

The upload fixture uses isolated owner profiles and receive-only inbox grants. Android creates a pairing transcript and signs its guest approval; Windows validates it, adds its actual host signature and binds its owner/trust profile. Android commits that completed receipt through `AndroidOwnerPolicy`. This is deliberate fixture setup through local control pipes, rather than an invitation, coordinator or native controller approval journey.

After the first real 32,768-byte range is accepted, the sender's fixture drops that response locally. Its journal must retain offset zero while the receiver reports the accepted range. The sender manager is closed and recreated, then explicitly resumes the original receipt with one preparation. This is manager recreation, not process death or a network disconnection. File contents and RPC continue to travel over the native encrypted channel.

Both destinations already contain a different owner file with the selected name. Completion must keep that original, publish exactly one additional copy, preserve the source, and pass a fresh published-copy proof. The driver compares each source hash to the opposite endpoint's saved-file hash. Each receiving grant is then withdrawn; a new preparation against the old target must be refused without another receipt or output file. The driver requires both checkpoint events, both withdrawals, all outcome fields and clean exits before producing the completed upload result.

Use the new instrumentation APK containing `NativeUploadProbe`:

```powershell
./tools/test-native-cross-platform.ps1 -Serial emulator-5568 `
    -ExpectedAvdName iconnect-large-files -NativeBundle $bundleDirectory `
    -TestApk $instrumentationApk -ExpectedApplicationSha256 $installedApplicationHash `
    -Suite uploads -FixtureDirectory $preservedWindowsFixtureDirectory
```

`-FixtureDirectory` is optional; it selects a preserved Release fixture build instead of the current build output. The driver still checks redirected paths and replaces only the copied role directory's transport DLL with the verified source-built candidate.

## Windows native folder-batch controls

Two additional Windows-to-Windows controls exercise the production private-source, sender and receiving engines over authenticated native peers. Each sends a six-item nested tree in both directions, retains empty directories, Unicode name text and zero-length files, recreates both sender stores after an accepted range reply is lost, resumes the original parent plan, checks all item outcomes, preserves collision/source originals and refuses a new plan after the receiving grant is withdrawn. One case permits listing without reading; the other preserves blind-inbox randomized names and checks physical results through the retained item receipts. Both pass within the 878-case selected Windows regression.

This control exposed and now covers the [Windows long-path attachment compatibility fix](windows-attachment-paths.md). It does not add an Android batch probe or a `-Suite batches` option to the public driver. The pinned ordinary-upload driver and frozen artifacts used by the active Android sequence remain unchanged.
