# Windows local file and folder batches

Follow-up: [missing batch history recovery](phase-60-windows-local-batch-recovery.md) adds conservative copy decisions and visible unattached-receipt controls, superseding this phase's earlier orphan-child-receipt limitation.

Windows can plan and copy selected files and folders without pairing, coordinator access or sharing approval. The local explorer supports up to 128 selected loaded items across display pages. Preview and details require one selection. Selection capture precedes asynchronous planning; changing the visible selection cannot replace captured sources.

## Reviewed, bounded source plans

`WindowsLocalBatchCopies` owns a separate `local-batch-copies` store with an exclusive native writer lease and pinned private directories. Plans are immutable source references, not private payload snapshots. Each records native root, ancestor and file identities, exact component paths, file versions and sizes. These references never enter a network file service or `StorageGrantStore`.

Planning includes selected folders, empty folders, nested folders and zero-byte files. It permits at most 4,096 items, 32 source path components, 2,048 component characters, 128 selections, a 4 MiB transfer manifest and an 8 MiB source journal. Eight source plans and 16 GiB of declared source sizes are retained at most. These are admission bounds, not an app-wide quota or a maximum-capacity performance claim. Overlapping selections, colliding top-level names, excessive trees and changed folders abort planning without committing a partial plan. Unsupported children with normal names receive explicit issue rows and are not followed. Invalid names abort planning.

Each reviewed plan stays frozen across restart. New source files are excluded. Each source operation opens native bound ancestors and rejects replacements, reparse points and hard links. Planned file identity, size and version must still match. A later hard link or changed file is refused. The source directory version is checked during planning; later additions do not invalidate the frozen plan or enter its copy list.

The private read adapter exposes only planned items. A selected file's synthetic root cannot list its siblings. Listings and root resolution use bounded pages; 128 selected files work without widening the 32-entry response limit. The shared manifest resolver now follows root continuations and rejects ambiguous roots. The local adapter has no mutation operations, peer identity or sharing grant.

## Publication and lifecycle

The native batch receiver creates new directories without merging or replacement. The destination review offers keep-both names, skip or fail for a conflicting item/subtree. It refuses a destination inside a selected source folder. Each file reuses checkpointed receiving, prefix/whole-file SHA-256 verification, no-replace publication, untrusted-origin marking, Windows attachment checks and read-back verification. Originals and existing destination content remain intact. This copies file data, without inheriting source alternate streams, trust or complete metadata.

Draft plans survive a canceled destination picker. The screen provides 20-item plan/result pages, destination review, progress, pause/resume, cancellation, terminal record removal and damaged metadata preservation/removal. Closing pauses work; restart requires explicit resume. Canceling retains completed files and folders and only cleans identified private partials. Missing source plans cannot authorize fresh reads; retained verified data uses the receiver's existing verification paths. Native picker, keyboard, visual and screen-reader behavior still require actual execution.

Local batch receipts participate in unidentified-part protection. The recovery service validates both parent and file receipts under the same ownership gate, protects paused parts, refuses active or unreadable ownership, and invalidates old removal reviews when receipts change. An existing local batch store cannot silently be omitted by a recovery consumer.

Completed file identities now remain in the batch receipt after the child transfer receipt is removed. **Verify completed destination…** reopens the recorded destination and every copied item by identity, checks SHA-256 for file data, and checks membership inside copied folders. The check runs without the original source and can be canceled. Older receipts without destination file identities remain readable and removable. The result describes the copy during the check.

For a move across local volumes, the reviewed destination and exact output name stay bound to the single-folder plan across restart. The copy fails on a collision. A fresh **Review original folder for recovery…** approval verifies both trees before moving the original into its source-volume vault. The saved tree is checked again while the destination files remain open. Interrupted final verification retains the original in recovery with an outcome that needs review. The [manual validation guide](physical-network-validation.md) covers the two-volume picker and recovery workflow in step 56.

Lifecycle testing exposed reentrant cancellation in the shared batch receiver: canceling a token could invoke an observer before its cleanup task was registered, starting duplicate cleanup. Cancellation now starts inside the registered worker. Reentrant requests obtain the same cleanup task, and disposal waits for it before releasing the native store lease.

## Verification and remaining gates

The final Release solution build passes with **zero warnings and zero errors in 14.34 seconds**. All **42 focused local-batch and receiving-part cases pass in 13 seconds**. Tests use generated data and actual Windows filesystem identities, including a 128-file selection, a rejected 4,097-item tree, native links, changed sources/ancestors, frozen plans, folder collisions, real partial-file pause/restart/resume, concurrent cancel/close, protected parts, damaged ownership and stale removal reviews. A separate case invokes the real Windows attachment worker; injected attachment outcomes in other tests are narrower evidence.

The first expanded lifecycle run had two failures: an invalid empty-search test query and the reentrant cleanup race described above. The query was corrected without weakening overlap checks, and cleanup registration was repaired in production. All 42 cases then passed on the corrected binaries. Local evidence: `.tools/phase59-cancel-fix-build.log`, `.tools/phase59-final-focused.log` (the failed expanded run), and `.tools/phase59-cancel-fix-focused.log` (the passing final focused run).

The first broad run passed 545 of 546 selected cases in 3 minutes 42 seconds. `Compact_receipts_free_detailed_capacity_and_closed_reset_rotates_the_replay_namespace` failed on a Windows access denial while renaming receiver-history metadata. Its isolated recheck passed on unchanged binaries in 314 ms. Inspection found no new local-batch access to that receiver store; the denial's cause is not established. Rename checks were not relaxed. Evidence: `.tools/phase59-final-regression.log` and `.tools/phase59-history-reset-recheck.log`. This intermittent native-history outcome remains recorded for filesystem/lifecycle review.

The final full rerun passes **all 546 selected Windows cases in 3 minutes 34 seconds**, using the same three previously recorded 4,096-item capacity exclusions; no new exclusion was added. Production storage, model, desktop, connectivity and proof DLLs, plus the test DLL, have matching SHA-256 identities before and after verification. Evidence: `.tools/phase59-final-regression-recheck.log` and `.tools/phase59-final-hashes-{before,after}.txt`. This passing rerun does not erase the earlier unexplained native access denial.

The physical test kit adds step 33 and remains **prepared, not run**. Windows GUI automation remains stopped after Escape. No Android source changes or new Windows–Android encrypted interoperability claims are part of this change. Android local folder batches, provider-safe management, full-capacity responsiveness, shared quota/history cleanup (including orphan child receipts after loss of a parent batch), additional filesystems/volumes, process/power loss, accessibility, packaging and independent security/release gates remain open in the [completion audit](completion.md). Remote batch capability advertisement remains disabled.
