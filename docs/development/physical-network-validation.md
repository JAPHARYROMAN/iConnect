# Physical Windows–Android network validation

This is the operator-run test requested for after implementation. It is prepared now; **physical-phone/separate-network results remain unverified**. A passing emulator or same-LAN run does not complete this gate. Use the final reviewed release builds when available.

The [focused native connection acceptance check](native-connection-field-validation.md) binds the SCTP/DTLS corrections to the actual Windows runtime and records first-failure outcomes across both initiating devices. Start there when validating the corrected transport, then continue through the broader workflows below.

## Setup

Use the [Windows release procedure](windows-release.md) and [Android release procedure](android-release.md) to verify the intended packages and signing certificates before installing the builds used in this test.

Use a Windows PC on one internet connection and a physical Android phone on mobile data. Turn the phone's Wi-Fi off and confirm its cellular connection works. Record the connection types, app versions and Android version. Use a reachable HTTPS coordinator with a valid certificate and a deliberately chosen STUN service. If you are operating the coordinator, check it externally before pairing. Configure STUN in Windows **Settings → Connection** and Android's **STUN address (optional)** field while disconnected using `stun:host:port` or bracketed IPv6. Both clients must use the same coordinator. Once paired and registered, either Windows or the phone's **Connect to computer** can start the direct connection. Record the initiator. A direct path can fail on restrictive networks, and the product has no relay fallback. [Coordinator setup and health check](coordinator-release.md), [connection behavior and verification gaps](phase-20-phone-connections.md)

Use generated test data and new destination folders. Do not use personal documents, a whole drive or credentials. Keep expected hashes on the PC, outside the folder being approved. Do not include invitations, QR codes, verification codes, private keys or personal paths in shared evidence.

Prepare a small fixture in Windows PowerShell:

```powershell
$fixture = ./tools/field-network-test.ps1 -Mode Prepare
$fixture | Format-List
```

The helper creates a new run directory, a `share` subfolder, and `expected.json` beside it. It never deletes existing content, changes app/OS settings, pairs devices or sends data. The default binary is 8 MiB plus 17 bytes; there are also text/Unicode, zero-byte, nested and empty-folder fixtures. Transferring them in both directions consumes at least twice the generated size. Use `-SizeMiB 64` only if a larger test is needed to make interruption observable and that mobile-data use is acceptable. Step 71 has separate storage and data requirements for files over 4 GiB.

If Documents is redirected, pass `-OutputDirectory` with an ordinary local folder such as one under Downloads. The helper refuses redirected path components. Keep `expected.json` beside the generated `share`, and approve only `share` in the app.

## Checks

1. **Fresh pairing.** Open both apps, configure the coordinator, display the Windows invitation and scan it on the phone. Check the matching code on both devices before approving. Confirm that pairing alone shares no folders.
2. **Authenticated direct session.** Connect to the paired phone from Windows. Both apps must report the authenticated direct connection. Record that state and confirm the phone remained on mobile data throughout. A coordinator-only connection is insufficient.
3. **Read-only boundary.** Approve only `$fixture.ShareDirectory` for this phone, initially read-only. Browse it on Android and preview `hello.txt` and the Unicode file. Creation/rename/move controls must be unavailable or denied. Confirm that no source data changed.
4. **PC → phone.** Copy the complete fixture folder into a new phone destination using the system picker. Wait for verified completion/publication. Check nested and empty folders and the empty file. An uncertain publication is a recovery case, not a pass.
5. **Phone → PC and hashes.** Approve only that received fixture folder on Android, read-only, while the app is open. Copy it back into a new PC destination. Run the verifier against the returned folder containing `_iconnect-field-run.txt`:

   ```powershell
   ./tools/field-network-test.ps1 -Mode Verify `
       -ManifestPath $fixture.ManifestPath `
       -ReceivedDirectory 'C:\path\to\returned\fixture-folder'
   ```

   Require `Verified : True`. The verifier checks every expected file's length/SHA-256, expected directories and unexpected items. App receipts and copied bytes must agree.
6. **Collision.** Repeat a copy into the same parent and choose keep-both. Verify the new copy separately. Verify the first copy again; it must remain unchanged. Exercise skip/fail where the UI offers them and record the individual outcomes.
7. **Interruption and resume.** Start another binary/folder copy, then briefly pause availability or interrupt the phone's data connection. Require an honest interrupted/paused state. If the Windows coordinator remains reachable while the direct path is lost, verify that Windows still shows the pairing and requires a fresh authenticated session for browsing. Restore connectivity, reconnect to the same trusted device and explicitly resume. Verify final bytes. Record partial/uncertain outcomes; do not treat them as complete or delete source data to resolve them.
8. **Windows background mode.** With its explicit option enabled, close the Windows window. Verify approved phone-side browsing/copying remains available. Relaunch Windows to reopen the existing instance. Pause availability and verify access ends; restart and confirm it remains paused. Quit should end the process. Keep Android open unless testing an explicitly selected notification-backed single-file transfer.
9. **Android lifecycle and reconnect.** First leave the phone UI with automatic reconnect off and without enabling a background transfer. New unrelated phone browsing must stop. Reopen and reconnect. Then deliberately enable **Reconnect to this computer while the app is open**. Interrupt/restore connectivity while the UI remains visible and verify a fresh authenticated session can return, while transfer queues remain paused until resumed. **Disconnect and pause** must stop retries and remain paused after restart; **Resume automatic connections** is deliberate. Backgrounding must stop automatic connection attempts; returning to the foreground may retry only when the saved choice is unpaused and still matches this pairing/address. Separately test selected single-file background transfer/notification pause controls and confirm reconnect does not create a new background session. Folder batches must pause when the UI leaves the foreground. See [Android reconnect behavior and remaining evidence](phase-21-android-reconnect.md).
10. **Revocation.** Revoke the phone on Windows, including while offline. Restore connectivity and require denial of old references/approvals. Fresh pairing must require fresh folder approval. Use only the generated fixture when testing allowed management actions.
11. **Availability consent and expiry.** Before starting a direct session, leave reports off on both devices and verify that no positive coordinator availability is shown. Disconnect, enable **Share availability with paired devices** on one device only, save and reconnect; a positive report still requires the other device's choice. Enable it on both, reconnect and allow a polling interval. A coordinator report must remain distinct from authenticated direct connection, and must not enable file browsing. Disconnect/close one app or interrupt its network and verify reports become unknown after lease/report expiry. Return Android to the background during a selected single-file transfer and require its availability reporting to withdraw while only that authorized transfer continues. Reopen deliberately. Verify disabling and revocation, then confirm direct connection attempts remain possible with reports off. Record failures and timing; this is approximate coordinator observation, not a guaranteed offline detector. See [paired availability](phase-22-paired-availability.md).

12. **Phone-initiated copy into Windows.** Create a new, empty generated-data destination on the PC. Approve it for this phone as **Contribute**, then test **Receive-only inbox** separately. On Android, use a local shortcut to the phone fixture from step 4 and **Prepare to send to computer** for `network.bin`. Wait for private preparation to finish; this must not create phone sharing approval. Connect, use **Load approved receiving locations**, select the test destination and send. Require matching verified-publication receipts on Android and Windows, then compare the received file's SHA-256/length against the original `network.bin` on the PC. The returned filename can differ; use the receipt. Repeat with an existing destination file and require its bytes to stay unchanged. For receive-only, directory listing, metadata reads and downloads must remain unavailable; received names use a unique suffix even on the first copy. Try read-only permissions and require denial without a new destination file. Pause/reopen/reconnect and explicitly resume/check the original receipt; require no duplicate after a lost acknowledgement. Verify the original phone file and private copy remain until a deliberate private-copy removal. Exercise Windows **Stop and discard this incoming partial…** only on generated data and verify published files stay intact. This step transfers an additional copy of the selected binary over mobile data. See [incoming-copy behavior and limits](phase-23-incoming-copies.md).

13. **Windows-initiated copy into Android.** On the phone, choose a new generated-data destination and explicitly enable **Receive new file copies**. On Windows, use **Transfers → Choose local file to prepare…** for the original `network.bin`; verify no new source sharing approval appears. Connect, load approved receiving locations, select the phone destination and send. Keep the phone open. Require a completed, verified-publication receipt and compare the provider copy's length/SHA-256 by copying it back to a fresh PC destination. Repeat with an existing same-name file and require that original to remain unchanged. Test **Use as receive-only inbox** separately: listing/metadata/reads must be denied, context must not expose directory activity, and incoming names must receive a unique suffix. **Use read-only sharing** must deny new incoming bytes. Interrupt, reconnect and resume/check the same receipt without an automatic extra copy. An uncertain provider copy is a review outcome; repeat finish must only verify the recorded copy. Test Android **Discard private staging…**, **Archive / reset incoming history…** and abandoned private staging cleanup only on generated data; require provider documents and the Windows original to remain. Remove the private Windows send snapshot deliberately and verify its original remains. This step adds mobile-data transfers. See [reverse uploads and provider limits](phase-24-reverse-uploads.md).

14. **Received-file security on Windows.** Use a fresh generated-data NTFS destination. Exercise both a Windows download (including a batch child) and a phone-initiated upload. A new completed receipt must include successful Windows attachment checks, and the received file must retain Restricted Zone origin metadata. With `$receivedFile` set to that generated copy, inspect it using `Get-Content -LiteralPath $receivedFile -Stream Zone.Identifier`; expect `ZoneId=4`. Verify its bytes normally. **Finalizing** or a final filename alone is insufficient. Pause during checks, then retry/check the same recorded copy and require no additional copy. Exercise **Check published copy security…**, review its exact location and cancel once; the file and receipt must stay unchanged. A deliberate recheck uses the recorded identity/checksum, including after peer access is revoked, and must keep that access revoked. Record installed security-provider/policy outcomes, failures and missing-helper/unsupported-storage behavior; never record a blocked or timed-out check as complete. Windows security providers can alter or remove a file. Test only harmless generated content; a successful check does not establish that the file is malware-free. Android provider receipts establish byte integrity and publication, with no portable malware-scan claim. See [received-file security](phase-25-received-file-security.md).

15. **Created receiving folder after reconnect.** In each direction, use generated-data destinations with Contribute / receive-new-copies permission. Create a remote test folder, disconnect/reopen/reconnect, refresh the remote operation history and use **Use this created folder for sending** on its successful receipt. Send a prepared generated file into the selected child folder, verify the destination bytes and keep the original. Create an empty nested folder as well. Require the same receiving folder to be used without another top-level copy. Revoke Create permission and require recovery/send denial. On a generated Windows destination, move the original folder aside and create another folder with its former name; recovery must reject the replacement. Repeat for Android only where the provider supports deliberate local movement. In a receive-only inbox, the actual created folder name must have a unique suffix, ordinary listing/metadata/reads must stay denied, and recovery must not reveal directory activity. An uncertain or legacy receipt must require review; do not treat name matching as recovery. Record this single-file/created-folder result separately from the outgoing batch workflow. See [receipt and identity limits](phase-26-created-folder-references.md).

16. **Private outgoing folder batches.** Keep the generated source folder unshared. In the sending app, prepare a private batch for the paired device, review its plan and queue it. Establish the authenticated direct connection, select a new approved receiving location, and use **Review sending batch…**. Repeat in both directions. Check that original sources stay intact, nested and empty folders and zero-byte files arrive, and each receipt agrees with the result. Use a fresh Contribute folder to verify the returned tree with the generated manifest. Repeat with a receive-only inbox and use the receipt names to locate the outputs. Require randomized inbox names and check that the sender cannot list the inbox. Record both build versions, the Android provider, and keyboard, TalkBack and screen-reader behavior. See [native batch controls](phase-41-native-batch-controls.md).

    Interrupt a second generated batch, reconnect to the same pairing and resume the retained plan. Completed items must not appear again as new copies. Repeat with Android leaving the foreground while an unrelated explicitly selected single-file job is allowed to continue; the batch must pause and resume only after foreground return and deliberate action. Withdraw Write/Create, then forget/re-pair the peer, and require the old plan to be refused in both cases. Use only generated copies when testing a moved/replaced receiving folder. Preserve uncertain provider items for review; never resolve uncertainty by silently creating another batch. Finally review removal of a private sending copy and confirm both the original source and completed receiving copy remain intact. Record per-item failures and any capacity/provider limitations separately from a pass.

17. **Mixed file/folder limits.** Use generated copies to start an ordinary file send alongside private folder preparation or sending. Try another outgoing copy while both are active. At most two payload preparations/sends may run at once; additional work must visibly wait or report the limit. Pause one, then deliberately retry the waiting copy and confirm it can progress. Restart with retained private copies and confirm the app still accounts for them. Review removal of one private copy and confirm the displayed retained size falls while its original and received copies stay intact. Repeat on both devices. Record **Not run** if the final native controls are unavailable. This small field check does not establish the 16 GiB per-peer or 64 GiB aggregate boundaries; those need the separate resource tests, without consuming that much mobile data.

18. **Stopping an outgoing batch.** Start another generated batch and stop it after some items arrive. Require new items to stop, completed files and created folders to stay intact, and private partial cleanup to reach a clear stopped state or an explicit review state. Reconnect and restart both apps; the same stopped plan must not resume or create another copy. An uncertain provider publication must remain visible for review. Start a separate generated batch alongside it and confirm stopping one does not stop the other. Record **Not run** if the final native controls are unavailable.

19. **Sender history and private copies — run after the complete history UI is implemented.** Archive an inactive generated send and confirm that its source snapshot and receiving files remain intact. Review private-source removal, restore its current job before confirming, and require removal to be refused. Archive it again, review/confirm source removal and verify the original source and receiving files remain intact. Finally review removal of local sender history; it must affect only that history and leave a second batch's records intact. Record **Not run** if the final native controls are unavailable.
