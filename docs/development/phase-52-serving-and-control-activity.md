# Serving and local-control activity

This phase extends the bounded local history from [phase 51](phase-51-local-activity-retention.md). It adds Windows serving outcomes and durable incoming-publication events, and Android settings/recovery outcomes. These records remain local observations, never permission records or complete forensic audit trails.

## Windows serving and incoming publication

The Windows storage layer exposes an optional sink accepting only compiled event/action/outcome kinds, an optional validated peer identity, byte count and compiled operation. It does not pass request/receipt objects, request IDs, filenames, paths, labels, file hashes/content or exception messages. Unrecognized operation values become a fixed unsupported-operation label, and invalid peer strings are removed.

The serving boundary observes responses after its operation gate and authorization callback have returned. Accepted responses, explicit refusals, errors and cancellation are distinguished. Successful byte-range writes/reads and ordinary status polling are omitted; their refusals/errors remain observable. Invalid request IDs are not copied into the journal. An accepted Finish request is not a completed-publication event.

Ordinary and scoped batch-file receivers separately emit completed/review/canceled events after their durable phase commits. Actual completed-file events follow the existing origin/attachment/integrity/publication checks; they cannot prove the file is malware-free. Parent batches emit terminal outcomes after their metadata commits. Replayed unchanged terminal phases do not produce another publication event. Sink exceptions are contained and cannot replace an operation's result or loosen its permission checks.

The controller owns a 64-command writer that batches serving observations for approximately 100 ms outside storage/permission locks. Consecutive matching observations within a one-second capture window can be grouped with bounded counts and checked byte sums. It commits one bounded history update per pending group of commands. Queue overflow and failed persistence increase a visible current-run dropped-event count. Overflow refresh notifications are throttled to avoid an unbounded UI-dispatch backlog under a request flood. History corruption stops writes and uses the existing preservation/reset flow; no receiving file or receipt is removed to repair history.

Clear, retention and reset commands share the writer's ordering barrier. Graceful close drains accepted observations after file workers stop; concurrent closes wait for the same writer, and later control commands fail instead of waiting behind close. Existing owner-action records remain synchronous and share the journal's store lock. Their ordering against queued serving records follows journal commit order; history is not a global transaction clock. Process death, storage failures or sustained overload can leave gaps.

The native Activity page shows fixed outcome labels, optional short peer fingerprints and dropped-event warnings. Diagnostic reports include only the aggregate dropped count, never individual entries or peer identities. Windows UI compilation does not replace visual, keyboard or screen-reader validation; GUI automation remains stopped after the user's Escape.

## Android local controls

Saved presence/reconnect preferences and selected destination changes now record specific compiled settings actions after the underlying save. Failed settings writes produce failure records while retaining the original control behavior. Editing an unsaved endpoint is not reported as a successful durable save.

Metadata preservation/reset, private incoming-part cleanup, reviewed sender/source archive removal, receiver item-history retirement and outgoing-history cleanup record distinct compiled recovery actions after the existing checks and work. A bounded continuation that returns false is recorded as needing further review; it is not labeled complete. Recovery exceptions and cancellation produce review outcomes because partial work may already have happened. No review token, archive ID, filename, URI, raw failure reason or original file content is copied into history. Review/cancel alone does not record a completed cleanup.

History's own clear/off/reset controls do not append a new row after clearing the journal. Recording off suppresses history without suppressing the actual settings/recovery operation. Original files, sharing and pairing authority remain governed by their original independent checks.

An older development Android binary does not recognize these new kind strings and must preserve rather than reinterpret them as supported history. Supported upgrade/downgrade handling remains a release gate.

When incoming batch-plan metadata needs review, its history card now appears beside the early recovery warning. The general recovery list routes that area to the dedicated batch-plan dialog, rather than offering an unsupported individual-record archive. A visible page counter accompanies its bounded 20-item pages. These controls keep the original preservation confirmation and do not create remote access.
