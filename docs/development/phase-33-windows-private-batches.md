# Windows private batch preparation

This implementation prepares private Windows batch snapshots. It is not yet connected to the native sending queue or advertised as an available batch capability. Receiver interoperability and complete sending/recovery controls remain release gates.

`WindowsBatchSources` prepares owner-selected files and folders without granting a peer access to their original locations. It builds a bounded manifest containing component names, directory relationships, file lengths, SHA-256 values and explicit per-item errors. Source paths, native identities and local authority records are not included in the wire manifest. Private plan IDs remain separate from the future receiver's timestamped batch intent.

Enumeration uses native relative opens and retained directory identities, rejects redirected/hard-linked sources, bounds roots/items/depth/path length, and checks folder changes. System and credential locations follow the existing Windows exclusions. iConnect's own private profile is excluded when an ancestor is selected. Locked or unsupported entries produce explicit errors with no descendants or copied contents. Changed sources stop preparation. These snapshots capture individual files; they do not claim a transactional snapshot of an entire live filesystem.

Each successful file is copied into a separate app-private plan directory. Its ownership receipt is flushed before payload writes. Preparation hashes the original bytes, flushes and closes the private writer, reopens the identified copy, and verifies the complete digest before committing its final receipt. The recorded last-write timestamp is taken after the writable handle closes, following the Windows [file-time guarantee](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times). Only a completely prepared canonical manifest can put the plan into Ready. Interrupted preparation retains a Failed record and all identified partial copies; it never resumes by selecting a source again implicitly.

A sender must open a `SourceReader` before its first remote effect and retain that reader for the entire attempt. Opening it checks the retained descriptor and hashes the complete private file. Its native handles omit write/delete sharing, using the Windows [sharing contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea); the private parent remains held while bounded ranges are read. Every range checks current owner/pairing authority and cancellation. A cached size or restored timestamp alone is not enough to skip the full digest. No original source is reopened for transmission.

There are eight private plans, at most four for one peer, two simultaneous preparations, a 16 GiB peer reservation and 64 GiB aggregate reservation. Physical admission leaves a 64 MiB margin and accounts for other active preparations. Small progress records avoid rewriting a full 4,096-item manifest for every file. A two-entry manifest cache checks native file versions before reuse. Cold load validates ready manifests, file receipts, native identities, sizes, timestamps and exact private directory contents. Missing, damaged or unowned metadata blocks new preparation rather than adopting data by name.

Private cleanup requires a short-lived, single-use owner review. The review records each file's native identity, size and version, validates the complete directory before deleting any payload, and rejects changed confirmations, added files and replacement folders. Revoked peer access does not prevent the local owner from reviewing and removing identified private copies. Original folders and receiver-side copies are outside this operation. Damaged or absent-object recovery still needs its complete native recovery workflow.

The subsequent [shared outgoing resource phase](phase-35-shared-outgoing-resources.md) joins storage reservations and worker limits with single-file sending on both platforms. Exact remote intent/receipt recovery, complete per-plan receiver accounting, queue controls, accessibility and fresh cross-platform/field evidence remain outstanding. The [completion audit](completion.md) retains those requirements. The [physical-network kit](physical-network-validation.md) remains ready for the user's later run after implementation.

## Verification

The solution builds with zero warnings and errors. Focused coverage contains **15 Windows cases**. They cover nested/empty/zero-byte sources, original-source changes after preparation, caller mutation of returned manifests, pairing withdrawal, private data and metadata corruption, restored timestamps with changed bytes, replacement private folders, one-manager native ownership, locked/sensitive entries, canceled preparation, reviewed removal after revocation, changed confirmations, added unreviewed files and held-reader exclusion of writers/removal. Cold load also refuses an unbound folder beside a failed intent; matching its plan ID alone does not establish ownership. The original 14-case focused run passed in four seconds, and the additional cold-recovery case passes in the final main regression.

A separate capacity test passes on the final build in **49 seconds**: one selected directory and **4,095 actual three-byte files** produce a 4,096-item canonical plan. Every file is privately copied, flushed, hashed and read back. Reopening the manager recovers the complete plan and the final file's verified bytes beyond ordinary upload receipt limits. The earlier run passed in 1 minute 23 seconds. This proves private preparation and restart, not sending those files over a native authenticated channel or publishing them at a receiver.

The final broader main regression passes **339 tests in 1 minute 9 seconds**, excluding the separately exercised private-source capacity case and the Windows receiver's earlier file-capacity case. No combined new full-capacity native-checker or fresh Windows–Android run is claimed. The source changes do not resume Windows Computer Use or change the existing desktop fixture process.

The Windows CI workflow now runs the main regression, receiver capacity, private-source capacity and isolated preview projects in separate steps. This keeps the two large storage cases apart from the preview deadlines. The local results above remain separate-run evidence; no remote GitHub Actions result is claimed.
