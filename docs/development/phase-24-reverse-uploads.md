# Windows sends into approved Android locations

This increment adds Windows-initiated file copies to Android through `uploads-v1`. Both platforms can now prepare a private source snapshot and send it into a receiver-approved location without sharing the source folder remotely. This is progress toward the [complete application](completion.md); final Windows–Android interoperability, physical-network execution and release gates remain open.

## Owner workflow

1. Pair normally. On Android, choose a folder with the system picker and approve it for the paired computer. Sharing initially remains read-only. Enable **Receive new file copies**, or choose **Use as receive-only inbox**. Receiving requires both Write and Create and actual persisted Android read/write permission. **Use read-only sharing** removes those incoming permissions.
2. On Windows, open **Transfers → Choose local file to prepare…**, choose the receiving device, then choose a normal local file. Preparation makes an immutable private snapshot with a full SHA-256. The original stays in place and no source sharing approval is created. Up to eight retained snapshots share a 16 GiB reservation.
3. Establish the authenticated direct connection. In Transfers, choose **Load approved receiving locations**, then explicitly select an approved location. A writable open remote-browser folder can also be used. A receive-only inbox is selectable without exposing its contents. Change the receiving filename before the first request if needed, then choose **Send to selected destination**.
4. Keep Android open. Completion requires the phone to verify the private staged bytes, publish a new provider document, reread that document and confirm its size and SHA-256. Windows displays the receiver's final name and outcome. Android shows paged incoming receipts and any uncertain publication.
5. After interruption, reconnect to the same pairing and choose **Resume / check receiver receipt**. The sender reuses the saved remote ID, epoch and destination. It does not automatically create another copy after an uncertain acknowledgement. **Prepare another receiver copy…** deliberately starts a new request after confirmation; earlier copies remain.
6. Windows **Remove private snapshot…** removes only its app-private snapshot and record, keeping the original and all receiver copies. Android **Discard private staging…** stops and joins verification before removing only the identified private stage. It keeps every provider document, including incomplete or uncertain documents.

For a completed send, Windows **Verify published copy…** asks a compatible Android receiver to reread the exact published document. The challenge binds the check to the recorded upload and current authenticated session. Android validates the grant, provider ancestry, name, byte count and SHA-256. A successful response can be collected once within 30 seconds of verification. Closing the receiving scope invalidates its result. The check returns receipt metadata and leaves the source, snapshot and provider file intact. Step 57 in the [manual validation guide](physical-network-validation.md) covers the paired workflow.

**Prepare a file for a move…** also captures the Windows original's native identity, parent and version. After publication, **Review original for recovery…** requires fresh confirmation. Windows opens the original with a handle that denies other writes and replacement, hashes it, then requests a new check from the same authenticated receiver. The original enters recovery only after the matching response and a final session check. The outgoing receipt retains the recovery transaction ID, and the private snapshot remains available. Step 58 in the [manual validation guide](physical-network-validation.md) covers the paired move and restore.

Android **Archive / reset incoming history…** disconnects, stops incoming verification, preserves receipt metadata and starts a fresh epoch. Provider documents and staged files stay in place. Earlier sends lose automatic receipt lookup and need a deliberate decision after inspecting the destination. Separately confirmed abandoned-staging cleanup removes only bounded, recognized, unreferenced private files. It rejects symbolic links, extra hard links and substituted identities. Metadata-backup cleanup remains separate from file cleanup. Archived metadata does not retain an Android OS-access lease; current sharing and other queue leases still do.

## Security and recovery behavior

The Windows sender binds each snapshot to its CNG owner identity/generation, pinned peer and pairing approval epoch. Legacy trust records receive a local epoch before a session starts; a new signed pairing supplies a new epoch. Source selection uses held local directory/file handles, rejects redirected components and extra hard links, and validates source identity and size across preparation. Source paths are not serialized into outgoing receipt records. The complete private snapshot is rehashed before any outgoing request; changed pairing or bytes stop the send before content transmission.

Both receivers negotiate `uploads-v1` only when their incoming host is present. Android's host requires the real peer-sharing policy; an offline local-browser shortcut cannot become a remote incoming authority. Each operation rechecks foreground availability, current pairing, current grant, Write/Create, exclusions and OS access. Write-only inbox context suppresses directory activity timestamps and versions; listing, metadata and reads retain their independent permission checks. Inbox names always receive a random suffix.

Incoming Android records bind the local owner, peer, pairing epoch, original SAF tree, grant and exact destination ancestor IDs/names. Private stages use unpredictable names, exclusive no-follow creation and device/inode/single-link checks. Synced 32 KiB writes precede atomic checkpoint saves. A repeated acknowledged range must match existing bytes. Cold resume validates the prefix chain; only extra unacknowledged bytes in the identified private stage may be truncated.

Verification and provider publication have separate durable states. The phone records creation intent before invoking the provider. A returned document must have a new ID in the approved destination, the requested name and a supported empty regular single-link seekable file descriptor. Opening uses nontruncating `rw`; existing/nonempty descriptors are rejected before content writes. Publication checks current authority and ancestry at bounded write boundaries, requires synchronization, then rereads the provider bytes. The completed receipt is saved before private-stage cleanup.

Provider creation can change names or lose its response, and providers own their underlying storage. This adapter therefore preserves uncertain documents. A saved provider URI can only be reread and verified during reconciliation; it is never rewritten. An unknown creation receipt never triggers automatic creation of another document. An excluded/renamed or incomplete document remains reviewable rather than being marked complete. Providers that cannot meet these checks are unsupported by this path. These checks are not a guarantee against a malicious storage provider.

Android enforces 128 receipts, 32 per peer, 16 GiB per peer and 64 GiB overall of active reservations plus retained completion receipts, two verification workers, private staging limits and a free-space reserve. Normal terminal receipts expire only outside the mutation replay window; active/uncertain records require owner review. Pruning reconciles OS leases and attempts identified terminal-stage cleanup. Windows limits retained snapshots and concurrent sends, persists requests before contacting the receiver and treats descriptor changes, lost responses and integrity failures as review/pause outcomes.

The full Release build and all 220 .NET tests pass: 212 core/storage/connectivity/model/coordinator tests and eight native preview tests.

Nine new Android device tests use an actual test DocumentsProvider, persisted grants, private journal files and authenticated native peers. They cover durable checkpoint restart/repeated ranges, receive-only privacy, read-only denial, provider ID reuse, lost creation receipts, foreground cancellation, no-rewrite reconciliation, corrupted prefixes, revoked grants, failed journal commits, owner history reset, orphan/symbolic-link cleanup, zero-byte/skip/fail and checksum mismatch. This emulator denies hard-link fixture creation; extra-link validation is implemented but that negative device fixture remains unproven. Native peer tests exercise `uploads-v1` negotiation and actual provider-byte verification. They are same-platform component tests and do not establish Windows–Android interoperability.

Android debug app/test and unsigned release builds succeed. All 20 JVM tests pass. After installing the final app and test APKs and verifying the installed app SHA-256 (`0624031395ffd3e8a06f2df4be9d97ec9071b88d019a1c35394985b0efa04db3`), all 108 device/UI tests pass in 133.126 seconds. Lint reports zero errors and 52 advisories, including eight new style/storage suggestions. The corrected test-package build has no Kotlin warnings.

The native Release Windows app was launched against a new offline fixture profile prepared with `IConnect.DesktopFixture --local-only --seed-upload`. Its Transfers page renders the private ready snapshot, quota description, destination status and actions. Network sending/loading controls stay disabled while disconnected. The receiving-name dialog opens, shows the existing name and cancels without changing the record; the original and private snapshot still have matching bytes. This checks that page/dialog, not a complete picker-to-phone journey or accessibility audit. The fixture build has zero warnings/errors. The test app and owned emulator are stopped afterward.

The [operator-run physical-network kit](physical-network-validation.md) includes the reverse-upload journey for execution after implementation. Fresh cross-platform upload verification remains pending: the earlier automatic approval review rejected launching the local coordinator as “blocked by policy.” That launch has not been retried through an alternative launcher. Native in-process peer tests do not close this gate.

`git diff --check` passes. Source and documentation remain uncommitted, with new files included through intent-to-add for review. No commit, push or deployment is performed.

Remaining requirements include fresh cross-platform and independent-network evidence, outgoing folder/batch workflows, complete native/accessibility review, large-file/disk-pressure/crash/provider matrices, inaccessible metadata/OS-lease repair and archive import, bandwidth/metered policy, received-file origin/security metadata and scanning, signed packaging and independent security review. SHA-256 proves byte integrity; it does not establish file safety.
