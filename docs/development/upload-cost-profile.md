# Android upload cost diagnostic

`UploadCostProbe` is an optional generated-data instrumentation probe for finding expensive stages in Android uploads. It uses the production `PhoneUploads` and `AndroidFileService` paths, private snapshots and receipts, and the test APK's Storage Access Framework provider. It reports source generation, private source preparation, payload/sender hashing, receiver finalization and independent source/output hashing separately.

The default payload is **67,108,881 bytes** (64 MiB plus 17 bytes), transferred in 2,049 ranges of 32 KiB. Only the `payloadMiB` argument is accepted, as a numeric string from 8 through 128. Each run generates fresh bytes, verifies both source and published output independently, preserves a pre-existing collision file, then disposes its own fixture data. The instrumentation is supplied by the separately installed test APK.

After building and installing the debug app and its test APK on a disposable emulator, run:

```powershell
# Replace this serial with the intended disposable emulator's serial.
adb -s emulator-5568 shell am instrument -w -r -e payloadMiB 64 com.iconnect.proof.test/com.iconnect.proof.UploadCostProbe
```

A successful run has terminal instrumentation code `-1` and an `uploadCostResult` JSON value. The JSON requires successful completion, exact range counts, independent hashes and collision preservation. This manual diagnostic does not run automatically as a JUnit test.

## Measurements and limits

Wall time includes the actual operation, probe sampling and scheduling. CPU time uses the target process's [`Process.getElapsedCpuTime()`](https://developer.android.com/reference/android/os/Process#getElapsedCpuTime()); it includes diagnostic, polling and garbage collection work and excludes the separate provider process. Binder transaction deltas use [`Debug.getBinderSentTransactions()`](https://developer.android.com/reference/android/os/Debug#getBinderSentTransactions()). Unavailable counters are JSON `null`, never zero. Receiver finalization stages are sampled every 20 ms; short stages can be missed. Request times are cumulative observations and must not be added to the phase times as extra work.

The diagnostic uses direct local service calls. It proves neither encrypted transport nor a physical network journey. Its smaller payload does not replace the unchanged **4,295,229,457-byte** `LargeFileTest`, its original timeout, interruption, lost-acknowledgement, reopening and independent verification requirements. The earlier [large-upload timeout](evidence/android-large-upload-timeout-2026-11-09.json) remains unresolved.

## Allocation changes

The candidate replaces per-byte locale formatting in `Rules.hex` with fixed-width lowercase digit lookup. JVM tests compare empty inputs, leading zeros, all byte values and 288 seeded binary vectors against an independent positive `BigInteger` radix conversion.

`StorageRules` now retains immutable reserved-name/protected-folder sets and its existing compiled device-port expression. `AndroidFileService` similarly retains its existing quiet-operation set. Names, Unicode encoding validation, authorization, provider checks and durability checkpoints retain their existing behavior. No per-request authorization result or provider metadata is cached.

The before/after records use the same diagnostic instrumentation, payload size, range count and emulator, with fresh generated bytes per run. A single pair of observations can show where time was spent; it cannot establish a general transfer speedup or complete the [application acceptance audit](completion.md).

## Observed pair on 9 November 2026

Both runs independently verify the source and published output and retain the collision original. The before app is `dd6f88a4…`, the candidate is `6eab422c…`, and both use instrumentation `846d4891…` on the owned API 35 emulator.

| Phase | Before wall seconds | Candidate wall seconds |
| --- | ---: | ---: |
| Source generation | 0.576 | 1.575 |
| Private snapshot preparation | 43.555 | 68.311 |
| Payload and sender hash | 32.517 | 55.765 |
| Receiver finalization | 26.424 | 37.389 |
| Independent source/output hashes | 0.182 | 0.172 |
| Whole probe, including setup | 104.125 | 164.594 |

Target-process CPU time is 40.675 seconds before and 70.387 seconds on the candidate. Binder counters are unavailable in both runs. The candidate is slower in this observed pair; the cause is not isolated. The allocation changes have no demonstrated whole-upload performance benefit. Repeated controlled measurements are required before making that claim.

The complete debug/test/unsigned Release build passes in 8m 48s. All 89 JVM tests pass, and lint has zero errors and 71 warnings. All 77 selected device cases pass in 97.722 seconds without failures or skips: the existing 53 receiving/sender checks and 24 storage cases. Installed application and test APK hashes match before and after execution. Raw diagnostic, regression and build outputs and exact artifact/source bindings are retained in the [validation record](evidence/upload-cost-validation-2026-11-09.json).

The subsequent [sender checkpoint work](android-sender-checkpoints.md) profiles this unchanged candidate and changes only the cadence of the sender's restart hints. Its evidence and results are recorded separately from this allocation comparison.
