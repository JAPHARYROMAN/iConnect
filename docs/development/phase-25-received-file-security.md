# Received-file origin and Windows attachment checks

Windows receiving now applies untrusted-origin metadata before publication and requires Windows attachment checks plus another byte verification before issuing a new completion receipt. This covers standalone downloads, their batch children, incoming uploads and the bounded synthetic transport inbox. This increment is progress toward the [complete application](completion.md), not a release or malware-free certification.

## What the owner sees

Files remain untrusted after SHA-256 verification. A Windows transfer can have a final filename while its status still says **Finalizing** or needs review: the file is already origin-marked, but attachment checks have not finished. A policy rejection, timeout, altered file, missing helper or failed metadata write cannot produce a new completed receipt. Existing destination files and original source files stay outside these operations.

The transfer cards distinguish completed Windows attachment checks from earlier receipts that did not record them. **Check published copy security…** is a deliberate local action with a review dialog. It checks only the recorded file identity and checksum, fetches no bytes and cannot publish an abandoned partial under a new name. The incoming-copy action still works after the original peer's grant is revoked and does not restore that grant. Fully received standalone copies can also finish their local checks offline after peer revocation. A changed Windows owner generation still requires the existing owner-policy recovery process.

Canceling or pausing during security finalization retains the recorded final name. A checksum alone cannot turn cancellation into a completed receipt. An explicit retry inspects the same recorded copy; an uncertain result does not start another destination copy automatically. Local rechecks are bounded and participate in normal application shutdown cancellation.

## Origin and platform behavior

The receiver writes a fixed `Zone.Identifier` stream with Restricted Zone (`ZoneId=4`) to its identified, single-link temporary file before accepting content or publishing a final name. A pinned device identity is not a verifiable web origin. iConnect supplies no invented source/referrer URL to Windows attachment services; the documented default for an unspecified source is Restricted Zone. [Microsoft's source/zone contract](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iattachmentexecute-setsource) explains this behavior.

The fixed stream API accepts no caller-supplied stream name. The base object remains held while its canonical path is used; the opened stream must have the same volume/file identity and one link. Metadata is bounded to 16 KiB, synchronized and read back. Existing other fields/sections are retained, including supported UTF-8 and BOM-marked UTF-16 evidence. Terminal NULs emitted by the Windows API are accepted; malformed, duplicated-zone or oversized metadata is kept for review. Unsupported filesystems or denied stream access currently leave the transfer unfinished. Broader filesystem handling remains a compatibility requirement.

After no-replace publication, a data-read handle that permits handler writes but denies deletion pins the exact filename. An attribute-only handle does not provide this guarantee; a negative test caught and corrected that distinction. The broker validates the same identity, single-link state and normal-file attributes. It invokes `IAttachmentExecute::Save` on the actual final filename, including its extension. It never calls Execute, Prompt, SaveWithUI or a no-virus-check variant.

Windows may consult its configured security providers and can alter or remove a file. iConnect accepts only an exact successful API result. It then reopens the same file with data-write sharing denied, verifies identity/length and the complete SHA-256 again, reapplies/checks the untrusted-origin stream and records security-policy version 1. Missing or changed data never becomes complete. A provider or privileged security service can still remove a file; the app does not promise to undo that. [Microsoft's Save contract](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iattachmentexecute-save) describes handler effects and attached evidence.

A successful Save result does not establish that antivirus was installed, that every threat was scanned, or that the file is safe. Windows policy can reject a file type even when the bytes are intact. Provider-specific cloud checks follow the operating system/security provider's own configuration; iConnect does not add a cloud scanner or route transfer bytes through its coordinator. No security preferences are changed or bypassed.

## Broker boundary and packaging

`IConnect.Attachment.Worker` is a small ordinary-user broker for the trusted operating-system attachment service. It is separate from the capability-free AppContainer used for untrusted preview parsing. The broker needs normal OS attachment-service access; it is not presented as a parser sandbox.

The native launcher creates the process suspended, supplies an explicit inherited-handle list containing only its two pipe ends, assigns a kill-on-close job, then resumes it. An explicitly inheritable owner-file handle is not inherited. Each job allows one process, limits broker memory to 512 MiB and forbids worker child processes. At most two brokers run. Requests have bounded path/identity fields, replies are exactly eight bytes, and the default elapsed deadline is two minutes. Cancellation, protocol overflow, worker failure and timeout terminate the owned job and close its handles. These limits govern the broker, not separately managed operating-system security services. The [Windows handle-list API](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) is used explicitly.

Build/publish targets include the self-contained helper beside the desktop, console host and receiving fixtures. A missing helper blocks completion. CI verifies the helper and runtime are present in the desktop publish output, along with the existing compiled XAML and preview helper. The deliberately faulty attachment fixture is included only in the test output.

## Android

Android's existing local receipts retain peer, destination, identity and checksum information. The UI explicitly distinguishes byte integrity from file safety. This build does not claim a portable malware scan or an OS-wide origin mark for arbitrary SAF provider documents. The [document-provider contract](https://developer.android.com/reference/android/provider/DocumentsContract.Document) exposes provider-dependent document operations and readable metadata, not Windows ADS semantics. Android's [media scanner](https://developer.android.com/reference/android/media/MediaScannerConnection) indexes media metadata; it is not used as malware-scan evidence. Newer optional content-classification APIs do not establish a malware verdict for this supported API/device range. Provider/device and applicable security integration remain review gates.

## Evidence and remaining work

Sixteen new Windows tests exercise actual attachment-service calls for benign `.txt`, `.pdf` and `.bin` names and native policy outcomes for generated, unexecuted `.cmd`/`.exe` names. They also cover origin evidence/encoding, malformed/oversized metadata, identity substitution, file/ancestor rename denial, handler byte changes, blocked/canceled/paused completion, cold same-copy retry, owner-only recheck after revocation, refusal to republish a partial, missing/failed/oversized/hung workers, child-process denial and owner-handle noninheritance. Native WebRTC regressions cover the synthetic inbox and real receiving paths with these checks enabled.

Locked restore and the full .NET Release build pass with zero warnings/errors. All 236 .NET tests pass: 228 core/storage/connectivity/model/coordinator tests and eight native preview tests. The complete suite includes the 16 new security cases; its core run takes 40 seconds. The final native launcher passes the intentionally inheritable owner-handle test. No attachment workers remain afterward.

Android debug app/test and unsigned release builds succeed, and all 20 JVM tests pass. The final installed debug APK's SHA-256 is `387e79d3eee8e0d5b228ed1433ea549347d13131037ddccdf92175d581ec69a5`; all 108 device/UI tests pass in 143.094 seconds. Lint has zero errors and 52 advisories.

Desktop publish output contains compiled XAML, both self-contained helpers and their runtimes. The published app is launched against a newly generated offline profile (`IConnect.DesktopFixture --local-only --seed-upload --seed-received`). Its completed receiving card shows the attachment-check result and continuing untrusted status. The local recheck review dialog renders the exact generated location/name, explains provider effects and cancels without changing the receipt. The copied/original bytes still match and `ZoneId=4` remains. This is a native page/dialog smoke check, not a complete accessibility or security-provider audit. The owned app and emulator are stopped afterward.

The [physical-network kit](physical-network-validation.md) includes an operator-run security check for after implementation. `git diff --check` passes. Changes remain uncommitted and new files are included through intent-to-add for review. No commit, push, deployment or OS security-setting change is made.

Remaining work includes broader installed security-provider/OS/filesystem and large-file/deadline matrices, metadata repair/import, final accessibility and lifecycle review, release signing/installation, physical phone/network execution and independent security review. Fresh Windows–Android validation remains pending after the earlier automatic approval rejection of the local coordinator launch; this increment does not retry that launch through another method.
