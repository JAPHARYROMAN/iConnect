# Transfer, recovery and remote-change activity

This phase extends [serving and control observations](phase-52-serving-and-control-activity.md). History remains a bounded local convenience record. It cannot authorize access, reconstruct every operation or prove that an interrupted request had no effect.

## Durable transfer outcomes

Windows now observes private single-file snapshots, private batch preparation, outgoing single-file and batch sending, and individual and parent downloads. Phase observations follow the existing durable state writes. A failed progress save cannot produce a completed event; the in-memory recovery fallback reports review. Routine byte-range progress does not create a history row per chunk. Incoming collision skips are also distinguished from completed copies.

Both platforms distinguish a skipped file and a terminal batch with skipped or failed items from a completely copied batch. A parent sender/receiver completion is labeled completed only when every retained item outcome indicates a completed copy. A terminal batch with other outcomes is labeled completed with issues. Planned total bytes are not presented as successfully sent bytes for that case. A folder download can retain the verified byte count of its actually completed children while reporting issues at the parent.

Private preparation acceptance describes a verified local snapshot, not receiver publication. Completed Windows downloads still require the existing attachment/origin and byte checks. Separate local rechecks report completion only when the current durable completed record has the current attachment-check policy. These checks cannot establish that a file is malware-free.

Observers accept only compiled action/outcome/operation values, a validated peer fingerprint and optional byte count. Filenames, paths, provider URIs, request/receipt/review IDs, hashes/content and exception text are excluded. Exceptions in observers cannot change a transfer's result or bypass its original checks. The bounded writer, off/retention/clear controls and recording-gap behavior from phases 51–52 remain in force.

## Reviewed Windows recovery

The desktop controller now records the result of selected metadata-preservation, private-part cleanup, incoming-history reset, receiving-part removal, source/sender store preservation, archive removal, receiver-history retirement, sender-history archive/restore/purge and private-source cleanup operations. Reviews and inventory reads alone do not claim a completed effect.

Successful work is observed after the existing operation returns. A bounded continuation returning false reports review because work remains. Exceptions also report review: partial effects may already exist. Original exceptions and all owner, identity, version, worker, confirmation and filesystem guards remain effective. The history does not retain the confirmation or replace the recovery journal. Resetting history itself does not append a new cleanup entry to the cleared journal.

Android outgoing history archive, restore and purge now have separate compiled labels. The legacy general cleanup label remains readable in existing development histories.

## Android remote changes and uncertainty

The phone observes one existing remote-change intent without issuing or retrying it. A successful result requires a structurally valid receipt matching the dispatched mutation ID, operation, requested name where supplied, and response status, with a succeeded phase and OK status. Missing, mismatched or pending receipts require review. Explicit permission/unsupported responses are refused; other definitive errors are failed.

Cancellation before dispatch can be labeled canceled. Once dispatched, a lost reply or cancellation is labeled review because the receiver may already have changed the filesystem. The original intent is not automatically repeated. A subsequent history-refresh failure cannot overwrite an already confirmed outcome. A move selection is cleared only after a matching successful receipt. The temporary receipt ID/name used for validation are not copied into activity.

The existing independent Android provider limitations and Windows management guards remain. This work does not implement unsupported provider rename/move semantics or establish fresh encrypted cross-platform interoperability.
