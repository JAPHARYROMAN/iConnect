# Windows change receipts and connection observations

This phase closes a Windows caller-side success gap and extends the bounded local activity introduced in [phases 51–53](phase-53-transfer-and-change-activity.md). It does not add filesystem permission or advertise another wire capability.

## Confirm the original remote change

The desktop now executes each create-folder, rename, move, recoverable-delete or restore intent through one receipt-checking boundary. It clones the caller's request, obtains the appropriate mutation/recovery namespace, checks the namespace token and cancellation, and assigns a fresh intent ID before dispatch. It never retries that change automatically.

A completed outcome requires a structurally valid receipt with the dispatched ID, operation, response status and requested name when supplied, plus a succeeded phase and OK status. An OK status alone is insufficient. Missing, mismatched, malformed or pending receipts require review and cannot reach the caller's success path. Explicit permission/unsupported results are refused; definitive errors are failed. An unexpected receipt on a refused context is also reviewed.

Cancellation before dispatch is canceled. Once dispatched, a lost reply or cancellation requires review because the receiver may already have changed files. The existing move selection remains available after an unconfirmed result; it is cleared only after confirmed success. An independently failed recent-history refresh does not erase a confirmed outcome. The controller still checks current selection, identity, session, grant permissions and generation through its existing request/management paths. Safe provider management and cross-volume semantics remain separate requirements.

Activity accepts only compiled operation/outcome values and a validated optional peer fingerprint. Temporary names, namespaces, request/receipt IDs, paths, content and raw exceptions are not passed to the history writer. Observer failures cannot change the operation result. History remains an incomplete local convenience record rather than permission or forensic authority.

## Separate coordination from direct authentication

`ProofClient` now reports compiled phases for connecting, authenticated, ended, failed, canceled, unavailable and revoked peer links alongside its existing display state. The desktop maps these phases to fixed local labels; it does not classify security outcomes by parsing diagnostic text. Direct completion is observed only after the existing authenticated readiness task succeeds. An unavailable peer produces refusal while leaving the coordinator available. A failed native/authentication attempt cannot produce a direct completion record.

The coordinator has separate requested, connected, canceled, ended and failed observations. Its completed connection does not imply an authenticated device channel. Owner disconnect records cancellation after the local generation/availability barrier has ended access. An ordinary remote end is labeled ended; exceptions are failed. Cleanup, actual OS process loss and journal persistence can still leave gaps.

Status observers are isolated individually: an exception in one observer does not prevent the others from receiving the state or change native authentication/file transfer. Revoking an unrelated pairing no longer emits a false disconnection for that peer or overwrites the active link's displayed state. Existing signaling signatures, pinned identities, DTLS binding, challenge/readiness checks, glare rules and generation barriers remain the authority boundary.

The same bounded 64-command writer, retention/off controls, fixed descriptions, dropped-event reporting and diagnostic exclusions continue to apply. These changes cover selected Windows connection and file-change paths. They do not establish complete authentication, pairing-failure or lifecycle coverage on both platforms.

## Verification and remaining gates

The final Windows Release solution/WinUI build passes with zero warnings/errors in **9.60 seconds**. All **18 focused cases** pass in **3 seconds**, comprising 14 new cases and four enhanced existing native/controller cases. Real storage cases exercise successful independent rename/move/delete/restore intents, permission refusal, caller-request preservation, receipt substitution (ID, name, operation, status, phase, absence and malformed metadata), lost replies, cancellation before/after dispatch and throwing observers. Generated source and receiving bytes are checked independently.

The actual desktop-controller/native Windows-peer journey verifies a valid creation despite a failed history refresh and a real move whose success receipt is removed. The move happens once, the original bytes reach the target, the pending move remains and history reports review rather than completion. The negative native connection case uses valid signaling from the pinned identity while the real channel presents a different device identity; an explicit open-channel check and the production identity/challenge rejection prove that it fails before authenticated readiness. Browsing stays unavailable and the coordinator remains connected. Additional cases cover a rejected coordinator handshake, cancellation during handshake, unavailable peers, both signed-offer collision orderings, throwing status observers and revocation of an unrelated pairing while the original authenticated channel still transfers files.

The full selected Windows regression passes **500 cases in 3 minutes 19 seconds**, retaining the same three separately recorded capacity exclusions as phase 53. After that run, the negative connection assertion was strengthened to require the actual open native channel and the specific production identity/challenge rejection. The final solution rebuild passes with zero warnings/errors in **9.95 seconds**, followed by all **18 focused cases** passing again in **3 seconds**. Production storage, connectivity, model and desktop hashes match before and after this final verification; the added assertion does not change production binaries. No Android emulator is running. Evidence: `.tools/phase54-windows-regression.log`, `.tools/phase54-windows-final-assertion-build.log`, `.tools/phase54-windows-final-assertion-focused.log` and `.tools/phase54-windows-hashes-{before,after}.txt`.

Initial compilation caught an omitted explicit event type and a test call to a nonexistent explicit answer method; the fixture now uses the native transport's actual offer-description flow. The production guards were not weakened. Earlier focused/build evidence is retained in `.tools/phase54-windows-release-build.log` and `.tools/phase54-windows-release-focused.log`.

Android source and artifacts were not changed or rerun in this phase; [phase 53](phase-53-transfer-and-change-activity.md) remains its latest recorded verification. Windows GUI automation remains stopped after the user's Escape. Fresh encrypted Windows–Android, physical-network, supported upgrade/downgrade, process/power-loss, storage/provider, sustained-load, independent security, signing and packaging gates remain open in the [completion audit](completion.md). The [operator kit](physical-network-validation.md) adds step 28 and corresponding result fields. It is prepared for the user to run after implementation and was not executed in this phase.
