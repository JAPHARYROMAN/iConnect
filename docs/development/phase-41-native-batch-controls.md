# Native batch preparation, queue and history controls

Windows and Android expose private batch preparation, sending and history in their transfer screens. Receivers with owner-backed storage advertise `upload-batches-v1` on direct sessions. The sender can use the capability after peer authentication. Batch requests still require the current pairing and an approved destination. Preparation and queueing preserve the originals and keep the snapshot private until the owner confirms sending.

## Owner workflow

On Windows, Transfers offers a review dialog for adding files and folders, selecting the paired receiver and choosing keep-both, skip or issue-on-existing-name behavior. Android offers bounded multi-selection in On this phone, including selecting a local folder shortcut as a root. Navigation and shortcut changes are guarded during preparation; leaving the local view requires explicit review and stops that view's source authority.

Both apps show private-copy preparation progress and display names without retaining original paths in the batch label. Labels are optional fields in the existing source and sender records, so older records retain a reference fallback. A plan review shows relative paths, empty folders, file sizes, source issues and collision behavior in pages of 50 items. Queueing requires another explicit review. A retained prior receiver intent requires the additional-copy choice; it is never inferred as a retry.

The sender queue displays ten records per page, including archived records. Sending requires the current pairing, an authenticated session, the peer's negotiated batch capability and a receiving folder with Write and Create permission. The confirmation binds the reviewed destination. Once a receiver intent exists, resume checks that original plan and destination. It does not create a replacement request after losing a reply.

Pause cancels local work. Stop waits for that job's local worker before controlling its original receiver plan. An unstarted queued job can be stopped locally while offline, retaining its private snapshot. A remote stop requires the original current pairing and a compatible authenticated receiver. Published and uncertain receiver copies remain for review.

Android preparation and sending wait on explicit cleanup-completion signals. A coroutine's terminal job state can be observed before its completion callbacks finish; joining the job alone therefore did not guarantee that the active record and worker slot had been released. The broad regression exposed this race in source cancellation. Idle/shutdown and per-job pause-and-wait now include callback cleanup, and cancel-all iterates a snapshot because cancellation can synchronously remove work entries. The cancellation test repeats the real blocked-read/cleanup cycle 16 times, and a sender case pauses an accepted range before immediately stopping the same original plan.

Result dialogs read saved metadata off the UI thread in pages of 50. They distinguish copied, skipped, issue, review-needed and unprocessed items. Saved terminal receiver outcomes remain visible beyond the sender's local item cursor. If the private source was deliberately removed, available receipt names are used, with numbered references for other items. Integrity completion is explicitly distinguished from file safety.

## Reviewed cleanup

Archive and restore operate on the same sender intent. Purge removes only archived local job metadata and item receipts, preserving private snapshots, originals and receiver files. It loses that job's resume/stop controls. Interrupted cleanup has a visible continuation action. Private-source removal has a separate native owner review and remains protected against a current retained sender job, including a restore between review and confirmation.

The receiver history is also paged. Terminal plans offer reviewed retirement of detailed metadata, retaining compact original parent outcomes. Pending retirement can be explicitly continued. A closed-history reset is available only after every plan and retirement operation has finished; the native store rechecks the condition, preserves a backup and changes the receipt namespace. Existing files remain intact. Forced recovery/reset remains a separate action with its own warning.

Cleanup loops call the bounded store primitives, yield between checkpoints and stop when their screen is disposed or the Windows Transfers page is left. An interrupted operation retains its durable checkpoint. Confirmation descriptors remain short-lived, single-use and bound to the metadata reviewed by the native stores.
